## 5 What

1. 新增 QML 模态对话框通用底座 `qt_show_qml_dialog`（无边框透明 `QDialog` + `QQuickWidget`，
   `exec()` 阻塞返回按钮下标），并为「确认关闭」实现具体入口 `cpp_confirm_close`。
2. 用 QML 自绘弹窗（`ConfirmClose.qml`，圆角 + 深浅色）替换原 `tm-widget` 实现的

3. 新增 `cpp_kill_tabpage`，把 `g_mostRecentlyClosedTab` 的标记时机从「关闭按钮点击时」
   后移到「真正 kill 之前」，修复「点取消后 tab 仍被错误隐藏」；关闭按钮在弹窗期间隐藏
   高亮，取消后按鼠标位置恢复。
4. 新增 `cpp-kill-tabpage` / `cpp-confirm-close` glue；构建加 `QtQuickWidgets` framework
   与 `moganqml.qrc` 资源。
5. 补 `qt_qml_dialog_test.cpp`（confirm-close 纯逻辑契约）与 `2021.scm` GUI 集成测试。

## 6 Why

原 `tm-widget` + `dialogue-window` 的异步机制有两个顽疾：
- **连点重复弹窗**：快速多次点关闭按钮，异步对话框并发弹出多个。
- **X 关闭后无法二次弹出**：异步对话框生命周期与触发动作解耦，关闭一次后状态错乱。

根因是「异步 + 非串行化」。改用同步模态 `QDialog::exec()`，阻塞直到用户选择，天然把连点
请求串行化，从根上消除上述两类问题。同时 QML 弹窗视觉更现代，并为后续从「Qt widget 导出
scheme」的旧弹窗机制逐步迁移到 QML 提供通用底座。

## 7 How

- **串行化**：`qt_show_qml_dialog` 内部跑一个无边框本地模态 `QDialog`（包一个加载了指定
  QML 的 `QQuickWidget`），`exec()` 阻塞返回用户点选的按钮下标（取消 / X / Esc → -1）。
  `exec()` 的模态特性天然串行化连点请求。
- **跨层接口**：正文与按钮文案由调用方（scheme 侧算好经 glue 传入）提供，i18n 走既有
  `qt_translate` 机制（与原 scheme 路径一致）。桥对象 `QmlDialogBridge` 以 `QDialog` 为
  parent，QML 按钮点击 / 拖窗以 `choose(index)` / `startMove()` 反馈回 C++，`QDialog`
  析构自动释放，无泄漏。
- **三重锁尺寸**：QML root 用 `anchors.fill` 无固定 implicit 尺寸，`QQuickWidget` 的
  sizeHint 会塌缩，导致 `exec()` 时窗口被压到约 100×30。用 `qw->setFixedSize` +
  `QLayout::SetFixedSize` + `d.setFixedSize` 三重锁定为 `DpiUtils::scaled(400×200)`。
- **透明视口**：用 `QQuickWidget::setClearColor(transparent)` 而非 `WA_TranslucentBackground`
  （后者对 `QQuickWidget` 不完全生效，默认白底会盖住 `QDialog` 透明，露出方角）。
- **标记时机修正**：原实现把 `g_mostRecentlyClosedTab=...` 写在关闭按钮的 clicked 回调里，
  早于 `confirm-close-dialog`。点取消时 kill 未发生但标记已设，导致后续刷新错误隐藏 tab。
  `cpp_kill_tabpage` 把赋值挪到 `kill_tabpage` 调用紧前，保证「只有真关闭才标记」。

## 8 后续修复：弹窗触发后主窗口标签栏拖动失效

### What
`qt_show_qml_dialog` 的 `QDialog` 构造从
`QDialog d (QApplication::activeWindow (), Qt::FramelessWindowHint | Qt::Dialog)`
改为 `QDialog d (nullptr, Qt::FramelessWindowHint | Qt::Dialog | Qt::Tool)`。

### Why
#3871 合入后用户复现：触发一次确认关闭弹窗、点取消关闭后，主窗口标签栏（qwindowkitty
标题栏）拖动整个窗口的功能失效；标签栏点击 / 关闭按钮等其他操作正常。

排查链路（关键证据）：
- `qwindowkitty` 的 `WM_NCHITTEST` 钩子日志：弹窗**前** `WM_NCLBUTTONDOWN wParam=0x2 (HTCAPTION)`
  → `WM_SYSCOMMAND SC_MOVE` → `WM_ENTERSIZEMOVE` 拖动成功；弹窗**后** `wParam=0x14 (HTBORDER)`
  → 没有 `WM_SYSCOMMAND`，拖动失败。
- 主窗口 `hWnd` 没变，titleBar rect 没变（`0,0 2560x63`），`isInTitleBarDraggableArea` 仍
  正常返回 true；但 qwindowkitty 在 hit-test 路径中走到 `HTBORDER` 分支。
- 根因：`Qt::Dialog` 模态 `exec()` 时，Qt 把 size constraints 传染到父主窗口，
  qwindowkitty 在 Windows 上随之把主窗口标签栏 hit-test 误判为 `HTBORDER`，弹窗关闭后
  该误判残留，标签栏拖动失效。

### How
- 加 `Qt::Tool`：工具窗口类型不参与主窗口的模态状态机，避免 Qt 把 size constraints
  传染给主窗口。`Qt::Dialog` 保留是为了语义（仍是模态对话框）。
- parent 改 `nullptr`：`Qt::Tool` 不需要父窗口；保留 `activeWindow()` 父反而可能让 Qt 重新
  把它视为子窗口走旧的 modal 路径。
- 默认 `ApplicationModal` 保持不变（串行化的关键）；不加 `WindowStaysOnTopHint`、不手动
  居中——`QDialog` 默认行为已足够，避免无复现就预先打补丁。

### 测试
- `qt_qml_dialog_test` 7/7 通过（钩子契约不变）。
- Windows 实测：触发弹窗 → 取消 → 反复拖动标签栏，主窗口跟随移动，问题消失。

## 9 后续修复（macOS）：弹窗触发后标签栏拖动永久失效

### What
改 vendored 第三方库 `3rdparty/qwindowkitty/src/core/shared/systemwindow_p.h` 的
`startSystemMove`：macOS 分支从「裸调 `window->startSystemMove()`」改为「先试系统级移动，
失败则回退到古典 API `WindowMoveManipulator`」——与该文件 Linux 分支、以及同文件
`startSystemResize` 的 macOS 分支完全同款模式（补齐平台一致性）。

### Why
#3871 的 Windows 修复（§8，弹窗改 `Qt::Tool + nullptr` 父）在 macOS 上**不生效**。经多轮
实测日志定位，macOS 根因与 Windows（HTBORDER hit-test 误判）完全不同：

macOS 上 qwindowkitty 的标签栏拖动靠 `CocoaWindowEventFilter` 状态机（press→PreparingMove→
首个 move→`startSystemMove()`）。`QWindow::startSystemMove()` 在 Qt 6.8 的 Cocoa 实现是
`[window performWindowDragWithEvent:NSApp.currentEvent]`，其返回 true/false **唯一取决于
`NSApp.currentEvent`（AppKit 事件栈顶）是不是鼠标类事件**（见 `qcocoowindow.mm:346-363` 的
switch）。

实测证据（在 `startSystemMove` 调用点打印 `NSApp.currentEvent.type`）：
- 正常拖动：`type=6 (LeftMouseDragged)` → `returns true`，窗口能动。
- 弹窗 `exec()` 关闭后：`type=29 (CursorUpdate)` → `returns false`；且此后**主窗口收到的
  每一个 mouseMove/mouseDragged 事件，`NSApp.currentEvent` 都恒为 29，再不回 6**——不是
  偶发夹带，是事件流被「冻结」在 CursorUpdate 上。

根因：模态 `QDialog::exec()` 期间 Cocoa 不向被阻塞的主窗口投递鼠标事件，Qt-Cocoa 走
「合成补救路径」为其合成鼠标事件（`qnswindow.mm` 注释：“Cocoa will not deliver mouse
events to a window that is modally blocked”）。**exec() 返回后该补救路径未还原**：主窗口的
鼠标事件持续走 Qt 合成派发，而非 AppKit 原生 `mouseDragged:`/`mouseMoved:` 调用栈；而
`NSApp.currentEvent` 只在 AppKit 原生派发栈内才会更新，于是它停在模态期间/关闭瞬间的某个
陈旧 CursorUpdate(29) 上不再更新 → `startSystemMove` 持续返回 false → 标签栏永久拖不动。
唯一恢复手段是重启应用。

这是 **Qt-Cocoa 平台插件在「模态会话 + 合成事件投递」上的缺陷**，不是 qwindowkitty、
不是 mogan 弹窗用法的问题，无法靠「校验 currentEvent 后跳过/重试」治本（currentEvent 本身
已损坏，重试多少帧都是 29）。

### How
`startSystemMove` 失败时回退到 `WindowMoveManipulator`（同文件已定义）：它装一个 event
filter，在 mouseMove 时用 `QCursor::pos()` 计算位移、`QWindow::setPosition()` 移窗，mouseRelease
收尾。**纯 Qt API、不依赖 `NSApp.currentEvent`**，绕过损坏的 currentEvent，确定性恢复拖动。

- 正常情况（`startSystemMove` 返回 true）：走系统级移动，行为完全不变，保留原生体验。
- 弹窗后失效（返回 false）：回退到 manipulator，拖动恢复。
- 与 Linux 分支、`startSystemResize` macOS 分支同构——qwindowkitty 本就在 Linux 上对不可靠的
  system API 用 manipulator 兜底，macOS 此前 move 是唯一裸调的例外，本次补齐。

### TODO（后续追踪）
本 fallback 是对 Qt-Cocoa 平台插件缺陷（模态会话结束后 `NSApp.currentEvent` 不再更新）
的 workaround。关键点：**`QWindow::startSystemMove()` 是 Qt 稳定公共 API（返回 bool），
签名不变**。等 Qt-Cocoa 内部修复该缺陷后，它会自动重新返回 true，本 fallback 自然不再
触发、行为自动退回原生 system move——**无需改任何代码**。

`systemwindow_p.h` macOS 分支有 `TODO(qt-cocoa)` 标记（grep 可定位）。仅在「确认上游已修、
且想恢复 macOS 原生拖动体验（磁吸到顶/分屏，manipulator 手动移动没有这些）」时才需清理
fallback；功能上保留无害（还能兜底「currentEvent 偶发非鼠标事件」的瞬态竞态）。升级 Qt
版本时可顺手回归测试：点弹窗取消后拖标签栏，确认仍正常即可。
