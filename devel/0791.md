# [0791] Collab: 修复段首光标错位

## What
修复了当光标位于段首时，被 Snapshot/Remote 光标恢复机制错误解释为前一段段尾的问题。

## Why
在 encode_path 到底层 Loro 线性字节偏移、再被 resolve_cursor 转换回 text_idx 并由 linear_ir_path_at_text_index 寻找路径的过程中，由于 text_idx 的降维（去除了段落标签等结构信息），前一段尾部与后一段首部对应的纯文本索引相同，导致其贪心匹配到了前一段段尾。

## How
为 linear_ir_text_index_of_offset 和 linear_ir_path_at_text_index 新增了 prefer_start 参数。如果在字节偏移转换阶段，恰好落在某文本节点的开头（byte_off == cur），则设置倾向（Intent）为段首。随后在通过 text_idx 寻找路径时，若倾向段首且当前节点长度大于0，则主动跳过当前尾部，由下一个节点来承接 0 偏移的匹配，从而完美重现原始意图。

## 补充修复：协同结构光标（Structural Cursor）与空行/with 块定位修复

### What
1. 修复了协同编辑中结构光标（如 `\big`、`\with` 等复合节点 OPEN/CLOSE 边界，如 `path ... 0` 与 `path ... 1`）在编解码过程中降维丢失的问题。
2. 修复了空行/空段落（如 `para ""` 或空 `para`）由于纯文本字符数（`text_idx`）均为 0 导致的二义性与光标漂移跳变问题。
3. 修复了在含有 `with` 等非原子子节点的 `concat` 结构中，`with` 前文本光标被误合并为无字符索引的结构路径导致远端光标消失的问题。

### Why
1. 原有逻辑在编码光标时将所有节点投射为纯文本字符索引 `text_idx`，消除了 `LI_OPEN` 与 `LI_CLOSE` Token，无法表达嵌套结构层级。
2. 空原子/空段落在纯文本坐标系中长度为 0，多空行对应的 `text_idx` 相同且重合，解算时会发生二义性折叠。
3. 原有的 `concat` 节点平铺合并逻辑未预先校验子节点是否全为原子节点，在包含 `with` 块等混合结构时，误将 `[0, 1]` 转化为 `[1]`（指向 `with` 节点自身而非字符）。

### How
1. **物理 Token 锚定与 Payload 标记**：
   - 扩展 `linear_ir_offset_of_path` 与 `linear_ir_path_at_offset_with_anchor`，为复合节点 OPEN/CLOSE 以及空原子节点引入 `'O'` (OPEN) 和 `'C'` (CLOSE) 锚点标志，生成形如 `T<hex>@O` 或 `T<hex>@C` 的 Payload。
   - 解码端匹配 `body_markup` 中唯一的 `LI_OPEN` / `LI_CLOSE` Token UTF-8 字节区间，直接解算为结构路径 `prefix * 0` 或 `prefix * 1`，绕过 `text_idx` 降维。
2. **Concat 安全合并校验**：
   - 在 `resolve_cursor` 执行 `concat` 合并前，先校验该 `concat` 节点的所有子节点是否均为原子节点 (`all_atomic`)，包含非原子节点时跳过合并，保留原始节点相对路径。

## 补充修复：MOD_ASSIGN 精确 splice + 恢复优先级再反转（CRDT 优先）

### 背景
上一轮「重构恢复权值」（让 `position_get` 优先、`resolve_cursor` 兜底）是为了规避 `resolve_cursor` 在结构编辑后退化为 `I<int>` 整数偏移的问题。但该退化本身有更深层的根因，且 `position_get` 优先在文档级结构重构下会给出错误位置。本轮定位并根治了这两个问题。

### What
1. `compute_markup_edit` 现为 `MOD_ASSIGN` 与 `MOD_ASSIGN_NODE` 提供精确字节 splice 翻译，不再走 coarse `body_seed_markup` 重 seed。
2. `stable_cursor_snapshot::restore` 再次反转恢复优先级：`resolve_cursor`（CRDT op-id 锚定）优先，`position_get`（tree_position 观察者）仅在 payload 缺失/退化/CRDT 失败时兜底。caret 与 selection 同步反转。

### Why（根因）
1. **`MOD_ASSIGN` 走 coarse re-seed 摧毁 op-id 锚点**：原 `compute_markup_edit` 对 `MOD_ASSIGN`/`MOD_ASSIGN_NODE` 落到 `default` 分支返回 `ed.ok=false`，`mirror_mod` 退化为 `body_seed_markup`——整 body 重建。这会让 LoroText 中存活字符的 op-id 全部重置，导致：
   - 对端 `encode_body_cursor_hex` 找不到原 op-id 锚点 → 返回空 → `encode_path` 退化为 `I<int>` 整数偏移。
   - 对端 `resolve_cursor` 解算整数偏移时，在段落边界/根级偏移上可能产生单元素 path，触发 `path_up(path_up(raw_p))` 的 `path_up(nil)` → `Throwing path is too short`。
   - 结构编辑（如回车 `\int` + Enter 拆分）频繁触发 `MOD_ASSIGN`（段落内容重写、`with` 清空等），故并发结构编辑时必崩。
2. **`position_get` 在文档级 remove+insert+assign 重构下漂移**：`tree_position` 观察者以裸 `tree_rep* ptr` 跟踪节点身份。当远端段落拆分表现为 `remove([],2,1)` + `insert([],2, document(...))` + `assign([2/3], ...)` 时，观察者所附节点的 rep 指针会在 `notify_assign` 的 `reattach_*` 与 remove/insert 配合下漂移到兄弟节点。实测（B2.log）：B 的光标在段落 3（TESTLINE2）末尾，A 回车拆分后 `position_get(cur_save)` 返回 `[2,1,9]`（段落 1/TESTLINE1 末尾），而 `resolve_cursor` 正确返回 `[3,0]`（新拆分段落起始）。观察者把光标「拉回了上一段」，导致 B 后续输入全部落到错误段落。

### How
1. **`MOD_ASSIGN` 精确 splice**（`moebius/Data/Convert/loro/linear_ir_ops.cpp`）：在 `compute_markup_edit` 增加 `case MOD_ASSIGN`——定位被替换节点的 OPEN..CLOSE 整段 markup，删除该段并原位插入新树 markup。只动被替换区域，存活兄弟与 op-id 全部保留。`case MOD_ASSIGN_NODE` 同理，只替换 OPEN token（改 label），保留内部子节点与 CLOSE。
2. **恢复优先级反转**（`src/Edit/Modify/edit_collab.cpp` `stable_cursor_snapshot::restore`）：caret 与 selection start/end 均改为先尝试 `resolve_cursor`（仅当 payload 非空且非退化 `0:0:I0`）；CRDT 成功即用其结果，否则才回退到 `position_get`。这样：
   - 有了精确 splice 后 op-id 不再丢失，`resolve_cursor` 成为并发编辑下可靠的 ground truth。
   - `position_get` 仅在 cursor 未就绪（JOIN 刚完成、payload 为退化 I0）或 CRDT 锚点被彻底删除时兜底。
3. **`resolve_cursor` 单元素 path 防御**：在 `path_up(path_up(raw_p))` 前检查 `is_nil(path_up(raw_p))`，单元素 path（根级偏移）直接返回 nil 而非 throw。
