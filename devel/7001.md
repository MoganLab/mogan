# [0705] 增强 Loro 协作服务端落盘健壮性，降低文档意外丢失概率

## What

为云文档协作服务端（`tools/loro-server/`，Node.js）的落盘链补强四项防丢措施：

1. **落盘 fsync 持久化**：每条 update 追加、snapshot/meta 写入、rename 之后刷盘，
   断电 / `kill -9` 下已 ack 的编辑不再停留在 OS 页缓存而丢失。
2. **`persistQueue` 容错自愈**：单条 update 落盘失败不再让该文档的落盘链中断
   （此前会静默永久停摆——编辑照常广播却永不落盘），改为保留内存态、尽快触发
   全量 snapshot 重新落盘补救。
3. **snapshot 备份兜底**：写新快照前保留上一代为 `snapshot.bin.bak`，
   `snapshot.bin` 损坏/为空/解析失败时回退读 `.bak`。
4. **`meta.json` 损坏容忍**：按 `updates.log` 帧数重建计数，不再因坏 meta 中毒落盘链。

## Why

旧实现的落盘链存在几处会导致**真实丢数据**的缺陷：

- 全链路无 `fsync`，断电丢最近编辑；「temp+rename」只保证原子性、不保证持久性。
- `persistQueue = persistQueue.then(...)` 链上任一 `await` 抛错（磁盘满、瞬时权限、
  坏 meta）即 reject，此后所有 update 的 body 被跳过——**静默永久丢写**，最危险。
- snapshot 直接覆盖无备份；`meta.json` 损坏即抛错并叠加中毒链。

本次目标是堵住这些缺口，在崩溃 / 断电 / 单次写盘失败 / 文件损坏等意外下
最大限度地避免文档内容丢失或落盘静默停摆。

## How

### `store.js`（磁盘层）
- 新增 `fsyncFile` / `fsyncDir`（best-effort，失败仅记日志不抛），由
  `MOGAN_LORO_FSYNC`（默认 `on`）控制；`fsyncEnabled()` 实时读 env 便于测试切换。
- `appendUpdate`：`appendFile` 后 `fsyncFile(updates.log)`（每条 edit 唯一一条 per-edit fsync）。
- `writeSnapshot`：`copyFile` 旧快照到 `.bak` → 写 tmp → `fsyncFile(tmp)` → rename →
  `fsyncDir` → 截断 `updates.log` 后 `fsyncFile`。
- `writeMeta`：`fsyncFile(tmp)` 后再 rename（meta 仅记账，不 per-edit fsync 目录）。
- `createDoc`：mkdir 后 `fsyncDir(docDir)` + `fsyncDir(dataDir)`，防新文档目录断电消失。
- `readMeta`：`JSON.parse` 容错，损坏走新增 `reconstructMeta`（按帧计数 updateCount、
  探测 snapshot 近似 snapshotSeq）；`ENOENT` 仍抛交上层。
- `readState`：snapshot 候选 `['snapshot.bin','snapshot.bin.bak']`，前者空/缺失/读异常回退后者；
  新增 `readSnapshotBak`。

### `registry.js`（内存层）
- `applyUpdate`：body 包 try/catch，失败时 `scheduleFlush()` 触发全量 snapshot 自愈；
  链尾 `this.persistQueue.catch(()=>{})` 保证永不 reject。自愈依据：影子已 `import`，
  `export({mode:'snapshot'})` 是全量，失败的 append 可被下一次成功 snapshot 覆盖恢复。
- `scheduleFlush`：内层 `flushSnapshot` 同样 try/catch，失败仅记日志、链保持 resolved；
  持续失败时每次 applyUpdate 重新 arm 定时器，形成 5s 级重试。
- `load`：snapshot `import` 包 try/catch，失败则重置影子、读 `.bak` 再试。
- `flushAll`：单篇 flush 失败 try/catch，不拖累其余文档的关停落盘。

- `tools/loro-server/registry.js`（改）：persistQueue 容错自愈、load .bak 兜底、flushAll 隔离。

## 验证

- `store.test.js` 8/8、`registry.test.js` 3/3、`validate.test.js` 1/1 全过。
- 真实 `data/` 9 个文档经修改后的 `readState`/`readMeta`/`load` 全部读出且影子加载成功。
- `server.test.js`（集成，spawn 服务端监听端口）在当前沙箱因 `listen EPERM` 无法运行，
  属环境限制（server.js 未改、服务端可正常启动恢复文档）；其覆盖的落盘/恢复路径已由
  上述单元测试与真实数据读取覆盖，需在有网络权限的环境/CI 补跑端到端（含 SIGKILL 崩溃恢复）。

## 备注

- 主动**不**改「广播先于落盘」（`registry.js` applyUpdate 内 broadcast 在 appendUpdate 之前）：
  改为「先落盘后广播」会给协作加 fsync 延迟；CRDT 幂等 import + 上述 snapshot 自愈
  已能收敛不一致，残余风险（服务器与源客户端同时崩溃且未重连）概率很低。
