## 5 What
把 `auto-backup-trig` 这条链路真正接到 autosave 插件上，让插件收到主进程 payload 后，用 `path-copy` 直接复制源文件到 backup 目录。

1. 保持主进程 `auto-backup-trig-payload` 只发送最小信息：`path`、`type`、`id`、`session-id`
2. 在 autosave 插件中新增目录生成、时间戳命名和 JSON payload 解析逻辑
3. 插件使用 `(path-copy source target)` 复制源文件
4. 目标路径格式落为 `$TEXMACS_HOME_PATH/system/backup/<doc-id>/<yyyymmdd>_<hhmmss>.tmu`
5. 修复插件目录创建时 `mkdir` 误收 `path` 对象导致的 type error

## 6 Why
当前 `auto-backup-trig` 只是把 JSON payload 发给 autosave 插件，插件并没有真正执行备份动作。因此虽然触发链路存在，但不会产生实际文件复制结果。

这次任务的目标不是改旧的 manifest/export/rolling backup 逻辑，而是只沿着 `auto-backup-trig` 这条新链路，让 autosave 插件具备最基本的“复制源文件到 backup 目录”的能力。

## 7 How
实现时刻意把职责拆开：

1. 主进程：
   - `auto-backup-trig-payload` 只负责提供源文件路径和 `doc-id`
   - 不再在主进程里预生成 `target`

2. 插件：
   - `autosave-home` 读取 `TEXMACS_HOME_PATH`
   - `autosave-dir` 生成 `$TEXMACS_HOME_PATH/system/backup/<doc-id>`
   - `autosave-target` 使用 `srfi-19` 生成 `<yyyymmdd>_<hhmmss>.tmu`
   - `ensure-parent-dir` 确保 `system/backup/<doc-id>` 目录链存在
   - `document->string` 从 `(document "...")` 负载中提取 JSON 字符串
   - `handle-copy` 解析 JSON 后调用 `path-copy`

3. 异常处理：
   - 插件通过 `autosave-log` 将成功、跳过和异常写到 `/tmp/debug.log`
   - 目录创建前显式把 `path` 对象转成字符串：`(mkdir (path->string path))`

本次实际验证：

- 手工排查 `/tmp/debug.log` 时发现并修复了 `mkdir` 接收 `path` 对象导致的 `(file-exists? path): path should be string`
