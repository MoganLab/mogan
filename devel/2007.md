# [2007] 基于 macOS 平台修复 C++ 测试

## 如何测试

```bash
# 单个测试
xmake b <test_target>
xmake r <test_target>

# 全部 C++ 测试
./bin/test_all
```

## What

修复在 macOS 平台（Apple Silicon / Qt 6.8.3）上批量运行 C++ 测试时的崩溃、失败与超时问题，让 `bin/test_all`（即 `xmake run --group=tests`）在 macOS 上能稳定跑完。这是 [2006](2006.md)（Windows 平台测试修复）的姊妹任务。

1. `qt_chat_tab_widget_test::test_beginEditTitle_shows_editor` 批量跑时 `SIGSEGV`（`EXC_BAD_ACCESS`）
2. `qt_tab_page_test::test_dirty_title_moves_star_to_close_slot` 失败，且单跑耗时异常（~15s）
3. `table_performance_test` 整体过慢（~21s），其中 `test_50x50_text_table` 无意义、`test_handle_decorations_performance` 规模过大

## Why

这些问题在 Windows/Linux 上不出现，仅在 macOS（Cocoa 平台插件）批量串行跑时爆发，导致 CI 不可靠、macOS 开发者每次跑全量测试都要手动干预或等很久。

- **崩溃（真实 use-after-free）**：`ChatSidebar` 析构时，`~QWidget` 派发 `CloseEvent` → 窗口失活 → 焦点离开正在编辑的 `titleEdit` → `QLineEdit::editingFinished` 信号 → 重入 `endEditTitle` → 访问正在销毁的 `items_`（`QMap`）→ `EXC_BAD_ACCESS`。这不是测试问题，是生产代码的生命周期 bug：真实使用中关闭一个"正在编辑标题"的侧边栏窗口同样会触发。macOS 触发而 Windows 不触发，是焦点转移 / CloseEvent 派发时序在两个平台插件上不同所致。
- **hover 测试失败**：macOS Cocoa 平台插件的 `QTest::mouseMove` **不会**向未 grab 鼠标的 widget 派发 `mouseMoveEvent`（实测 `QTMTabPage::mouseMoveEvent` 根本不触发，`underMouse()` 为 `false`）。于是 `m_hoverOnCloseArea` 永远不变 `true`，dirty 标签页的关闭按钮不显示，`QTRY_VERIFY` 一直重试直到超时（约 15s 才放弃），既失败又慢。Windows 平台插件对 `QTest::mouseMove` 的合成事件处理不同，能正常派发，所以通过。
- **表格性能测试过慢**：`test_50x50_text_table` 与已保留的 `test_20x20_text_table` 结构完全相同，只是规模 50x50，断言仍是永真的 `QVERIFY(time>=0)`（[2006](2006.md) 删过一批同类无意义性能测试，这一条当时漏网）；`test_handle_decorations_performance` 对 `{20,30,40,50}` 四个规模档各跑 11 次 typeset，50x50 带 decoration 单档就要反复 typeset，是该套件耗时的主要来源。

## How

### 1. 修复 `ChatSidebar` 析构期信号重入（`qt_chat_tab_widget.{cpp,hpp}`）

#### 背景

`ChatSidebar` 持有 `QMap<string, SidebarItem> items_`，每个 `SidebarItem` 内含一个内联标题编辑器 `QLineEdit* titleEdit`。`beginEditTitle` 会让 `titleEdit` 获得焦点进入编辑态；`endEditTitle` 负责收尾。`titleEdit` 的 `returnPressed` / `editingFinished` 信号连接到 `endEditTitle`：

```cpp
connect (item.titleEdit, &QLineEdit::editingFinished, this,
         [this, sid= sessionId] () { endEditTitle (sid, true); });
```

#### Bug

析构 `ChatSidebar` 时的调用链（lldb 抓到的栈）：

```
~ChatSidebar                          // 用户代码，函数体执行完才析构成员
└─ ~QWidget                           // 基类析构
   └─ QWidgetPrivate::close → QWindow::close → 派发 CloseEvent
      └─ handleClose → hide()
         └─ setActiveWindow → setFocusWidget(focus=nullptr)   // 焦点转移
            └─ titleEdit::focusOutEvent
               └─ emit editingFinished                          // 信号重入
                  └─ endEditTitle(sid, true)
                     └─ items_.find(sessionId) → QMap::detach() // 拷贝 std::map
                        └─ 从悬空 key 构造 string → EXC_BAD_ACCESS
```

关键点：`editingFinished` 在 `~QWidget`（基类析构）期间被同步派发，此时 `endEditTitle` 重入，而 `items_` 的内部状态已不可靠（`QMap::find` 触发写时复制 `detach()`，深拷贝节点时访问了非法内存）。

为什么单独跑该用例不崩、批量跑才崩、Windows 不崩：

- **单独跑**：窗口是真正的活动窗口，析构时 `titleEdit` 作为子对象先于信号路径被处理，不 emit `editingFinished`。
- **批量跑**：前一个用例的 `cleanup()`（`cleanup_qt_top_level_widgets`）隐藏了顶层窗口，改变了焦点时序；本用例 `sidebar.show()` + `beginEditTitle` 让 `titleEdit` 持有焦点，测试结束析构 sidebar 时焦点转移路径恰好命中了重入。
- **Windows 不崩**：Cocoa 与 Windows 平台插件在 CloseEvent / 焦点转移的派发时序上不同，Windows 未触发该重入。

#### 修复

在 `ChatSidebar` 加一个析构守卫 `bool destroying_= false`，并在 `endEditTitle` 开头检查：

```cpp
void ChatSidebar::endEditTitle (const string& sessionId, bool accept) {
  // 析构期间 Qt 会派发 CloseEvent → 焦点离开 titleEdit → editingFinished，
  // 进而重入到这里。此时 items_ 可能已进入销毁流程，访问会导致 use-after-free。
  if (destroying_) return;
  auto it= items_.find (sessionId);
  ...
}
```

新增 `~ChatSidebar()` 析构函数，开头置位守卫并断开所有 `titleEdit` 的信号连接（双重保险：即使有其它信号重入路径也不会再回调到 `this`）：

```cpp
ChatSidebar::~ChatSidebar () {
  destroying_= true;
  for (auto it= items_.begin (); it != items_.end (); ++it) {
    if (it->titleEdit) it->titleEdit->disconnect (this);
  }
}
```

注意 `items_` 遍历用传统迭代器（项目自定义容器 / QMap 按规范不用 range-for）。`disconnect(this)` 断开所有从 `titleEdit` 连接到 `this` 的信号槽。

#### 生产鲁棒性收益

这不是只为了让测试通过的改动——它修掉的是一个真实 use-after-free：用户在侧边栏"正在编辑会话标题"时关闭窗口，理论上同样会触发崩溃。守卫让析构期不再处理任何编辑收尾逻辑。

### 2. macOS hover 测试改用合成事件（`qt_tab_page_test.cpp`）

#### 背景

`QTMTabPage` 的关闭按钮在 dirty（未保存 `*`）模式下，仅当鼠标 hover 到关闭按钮区域时才显示。可见性由 `updateCloseButtonVisibility()` 决定，dirty 分支依赖 `m_hoverOnCloseArea`：

```cpp
bool shouldShow = ... &&
                  ((!m_isDirty && (underMouse () || isChecked ())) ||
                   (m_isDirty && m_hoverOnCloseArea));
```

`m_hoverOnCloseArea` 在 `enterEvent` / `mouseMoveEvent` 里根据 `isPointerOnCloseArea(pos)` 更新。

#### Bug

测试用 `QTest::mouseMove (&tab, closeCenter)` 把鼠标移到关闭按钮中心，期望触发 hover：

```cpp
QPoint closeCenter= closeBtn->geometry ().center ();
QTest::mouseMove (&tab, closeCenter);
QTRY_VERIFY (closeBtn->isVisible ());
```

在 macOS 上探针确认：

- `closeBtn` 的 geometry 正确（`QRect(192,7 18x18)`，中心 `(200,15)` 在 220x32 的 tab 内）
- 但 `QTMTabPage::mouseMoveEvent` **根本没被调用**
- `tab.underMouse()` 为 `false`

即 macOS Cocoa 平台插件的 `QTest::mouseMove` 不向未 grab 鼠标的 widget 派发 `mouseMoveEvent`。Windows 平台插件行为不同，能正常派发。

#### 修复

不用 `QTest::mouseMove`，改为直接合成一个 `QMouseEvent(MouseMove)` 并 `sendEvent` 给 tab，可靠触发其 hover 检测逻辑：

```cpp
QPoint closeCenter= closeBtn->geometry ().center ();
// macOS (Cocoa) 的 QTest::mouseMove 不会向未 grab 鼠标的 widget 派发
// mouseMoveEvent，因此直接合成一个 MouseMove 事件投递给 tab，触发其
// hover 检测逻辑（等价于 Windows 上鼠标移入关闭按钮区域）。
QMouseEvent moveEvent (QEvent::MouseMove, closeCenter, tab.mapToGlobal (closeCenter),
                       Qt::NoButton, Qt::NoButton, Qt::NoModifier);
QApplication::sendEvent (&tab, &moveEvent);
QTRY_VERIFY (closeBtn->isVisible ());
```

补 `<QApplication>` 和 `<QMouseEvent>` 头文件。修复后该用例从 ~15s（一直重试到超时）降到 ~0.2s。

### 3. 精简 `table_performance_test`

- 删除 `test_50x50_text_table`：与 `test_20x20_text_table` 结构相同，仅规模更大，断言仍是永真的 `QVERIFY(time>=0)`，是 [2006](2006.md) 漏删的无意义性能测试。
- `test_handle_decorations_performance` 的规模档从 `{20, 30, 40, 50}` 缩减为 `{20, 30}`。该用例有真实断言（验证 decoration 扩展后 `rows_after > rows_before`、`cols_after > cols_before`），予以保留，只去掉过慢的 40/50 两档。20/30 已足够覆盖 `handle_decorations` 的扩展路径。

效果：整个 `table_performance_test` 套件从 ~21.7s 降到 ~2.0s，8 个用例全部通过，真实断言保留。
