## 2 设计：树 ↔ Loro 的映射

骨干用 **LoroTree（可移动树）**：稳定节点 ID（TreeID）+ 分数索引子节点排序 + CRDT 安全 move/insert/delete，天然适配文档树。

每个 Mogan 树节点 ↔ 一个 LoroTree 节点：

| Mogan 节点 | LoroTree 节点字段 |
|---|---|
| 复合 `op>0` | `kind="compound"`，`label=<op 名字>`，子节点按序 |
| 原子 `op==0` | `kind="atomic"`，`text=<字符串>` |
| generic `op<0`（罕见） | `kind="generic"`，`label="generic:<op>"`，子节点按序 |

关键决策：
1. **标签存人类可读名字**（`"paragraph"` 而非 `op`），与 tmu 一致、前向兼容改名；导入经 `STD_CODE`/`make_tree_label` 反查回 op。
2. **Phase 1 原子串存普通字符串值**（非 LoroText）。Phase 2 再升级为 LoroText 子容器支持字符级并发。
3. **CRDT 范围仅 body 正文**（用户确认）；style/initial 等元数据不进 CRDT。

## 3 分层（隔离 Loro 依赖）

把转换拆成两层，使映射逻辑可在不依赖 Loro 时编译与测试；FFI 用 opt-in 开关 `libloro`，默认关闭不拖累主构建。

## 6 What（本次）

- 建 `LoroIRNode` 中性表示（compound/atomic/generic + label/text/有序 children）。
- 实现 `tree_to_loro_ir` / `loro_ir_to_tree` 双向深度映射，标签走 `CONSTRUCTOR_CODE`/`make_tree_label`。
- doctest 覆盖各类节点往返相等。

## 7 Why

- **为何先做依赖无关核心**：loro-c 是 Rust 库、沙箱无法抓取/构建，且 `loro.h` C API 签名需对版本核对。把映射逻辑抽到不依赖 loro-c 的 L1，可在沙箱立即编译与测试，证明映射忠实；L2 FFI 薄层隔离后，接入库只是机械翻译，且不受 loro-c 版本变动牵连。
- **为何标签存名字而非 op int**：op int 跨版本不稳（`STD_CODE` 随版本变），名字稳定且与 tmu 一致；导入时反查即可。
- **为何用 LoroTree 而非 LoroList/LoroMap 堆出树**：LoroTree 原生可移动树（move/insert/delete 全 CRDT 安全），是文档块增删重排的正确原语；L1 的 IR 正好镜像这一结构。

## 8 How

- **tree→IR**：`is_atomic` → 存 `text`；`is_compound` → `label=to_string(L(t))` + 递归子节点；`is_generic` → `label="generic:"+as_string((int)L(t))`。
- **IR→tree**：atomic → `tree(text)`；compound → `make_tree_label(label)` 得 op，`tree(op,n)` 填子节点；generic → 去前缀 `as_int` 还原 op。
- **泛型往返**：op<0 用十进制存取（`as_string(int)` / `as_int(string)`），保证负 op 忠实还原。

## 10 Phase 2/3 增量：本地 WebSocket 转发测试工具

为验证两个编辑器打开同一文件的协作编辑，新增了一个最小 WebSocket 转发链路。

### 10.1 What

- `tools/loro-relay/`：基于 Node.js `ws` 的本地转发服务器，按 room（文档路径）广播二进制 Loro update。
- `src/System/Link/loro_relay_client.{hpp,cpp}`：非 Qt 的 C++ WebSocket 客户端，独立线程管理 socket，通过队列与主线程交互。
- 编辑器接入：
  - `src/Edit/Modify/edit_modify.{hpp,cpp}`：首次 seed Loro shadow 后订阅 local-update，把本地增量发给 relay；收到远端增量后调用 `apply_remote`。
  - `src/Texmacs/Server/tm_server.cpp`：在 `interpose_handler` 中轮询所有 relay client，及时处理远端更新。
- 构建开关：`xmake f --libloro=y --loro_relay=y --qt_frontend=n` 启用 `LORO_RELAY_ENABLED`。
- 默认连接地址 `ws://127.0.0.1:8765`，可通过环境变量 `MOGAN_LORO_RELAY` 覆盖；连接失败静默降级为单机编辑。

### 10.2 Why

Phase 1 只能验证 snapshot 往返；Phase 2/3 需要**两台真实编辑器并发编辑**才能验证增量同步。先做一个本地 JS 转发服务器，可以：

1. 不依赖外部网络/云服务，秒级启动。
2. 保持 C++ 端网络代码最小化，不引入 Qt 网络库。
3. 服务器只做转发，CRDT 合并由两端 Loro 各自完成，逻辑清晰。

### 10.3 How

- JS 服务器协议：
  - 客户端连接后先发文本帧 `JOIN <room_id>`。
  - 后续二进制帧视为 Loro update，服务器广播给同 room 的其他客户端（不回发 sender）。
  - 服务器保留每个 room 最后一条消息，新加入者收到该消息作为初始基线。
- C++ 客户端线程：
  - `start()` 启动线程做 TCP 连接、WebSocket 握手、发送 JOIN，然后循环：发送队列中的本地 update + `select` 读取远端 update。
  - `send_update()` 主线程入队；`poll()` 主线程取出收到的远端 update 回调。
  - 收到远端二进制帧 → `loro_relay_on_update` → `apply_remote(bytes)` → Loro diff 出 mods → `edit_announce` 应用到 buffer。
- 在 `edit_modify_rep::start_editing()` 中懒启动 client：取 `get_name()` 作为 room，尝试连接默认地址。

### 10.4 修复的顺带问题

`mirror_loro` 和 `route_through_loro` 形参为 `const modification&`，但 `modification` handle 的 `operator->` 非 const，导致 `mod->k` / `mod / rp` 无法编译。改为 `modification m= copy (mod);` 后用 `m` 访问。
