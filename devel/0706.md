# [0706] 修复 LAN 下大帧 WebSocket 上行卡死（libcurl ws_flush 忙转）

## What

修复客户端向协作服务端上行**大体量 Loro update**（粘贴大图，单帧 ~0.5–1.3 MB+）
时连接卡死 / 服务端收不到的问题。最终落点在原生 WebSocket 客户端
`src/Plugins/WebSocket/libcurl/tm_curl_websocket_client.cpp`：

1. **`SO_SNDBUF = 4 MB`**（关键）：握手后调大 socket 内核发送缓冲，使整帧可一次性
   缓冲进内核、由服务端按自身读速消化，不再触发 libcurl `ws_flush` 的 EAGAIN 忙转。
2. **`CURLWS_OFFSET` 分帧 + `header_written`**：把一条大消息作为单个 WebSocket 帧
   分多次 `curl_ws_send` 发送（64 KB/次），帧头只在首调写一次（带 MASK+FIN），
   杜绝重试时重复帧头损坏帧流。
3. **`poll(POLLOUT)` 闸门 + `POLLERR` 检测**：发送前确认 socket 可写，避免在 socket
   满时盲目 `curl_ws_send`；socket 出错（对端关闭）即时 surface 为断连而非「等可写」永悬。
4. **`offset` 按 `sent` 推进（OK 与 AGAIN 均推进）**：与 libcurl 内部 `payload_remain`
   同步，避免重传已入帧字节造成载荷重复 / 缺失。

## Why

环回（127.0.0.1）永不复现，LAN 大帧必现，且经历了多轮错误假设才定位到真根因：

- 早期现象是服务端报 `RSV2/RSV3 must be clear` / `MASK must be set` / `Checksum mismatch`
  ——帧流被损坏。定位到旧实现的 `CURLWS_OFFSET` 分帧在 `CURLE_AGAIN` 重试时会以
  `fragsize=total` **重发帧头**，造成「重复帧头」错位。
- 修正帧格式后，客户端能完整发帧，但 worker 线程在发送途中 **100% CPU 钉死**、
  服务端 `paused=false readableLen=0`（服务端无辜、干等）。最终确认根因：
  **libcurl 的 `ws_flush(complete=TRUE)` 在内核发送缓冲满、`send()` 返回 `EAGAIN`
  时，源码是 `n=0; continue;`——纯用户态忙循环、不 sleep、无退出**。
  大帧突发填满内核 send buffer 即把 worker 钉死，再发不出一字节，服务端干等。
  `poll(POLLOUT)` 闸不住它（poll 只保证 ≥1 字节可写，`curl_ws_send` 要写 64 KB，
  写 1 字节后又 EAGAIN，继续忙转）。环回无背压、缓冲不满，故本地不复现。

这是 libcurl `CONNECT_ONLY` WebSocket 发送大块的固有缺陷，无法从 `curl_ws_send`
外部关闭；调大 `SO_SNDBUF` 让整帧先落内核是当前最稳妥的缓解。

## How

### `tm_curl_websocket_client.cpp`（worker 线程，仅用 std:: 类型，不碰 lolly）

- `worker_main`：CONNECT_ONLY 握手完成后，取 `CURLINFO_ACTIVESOCKET` 的 fd，
  `setsockopt(SO_SNDBUF, 4MB)`；`MOGAN_LORO_DEBUG` 下 `getsockopt` 回显实际值。
- `process_tx_queue`（重写发送循环）：
  - 外层遍历 `tx_queue`；每条消息内层 `while (offset < total)`：
    - `stop_requested` 检查（让 `disconnect()` 能及时打断大帧）；
    - `poll(fd, POLLOUT, 25ms)`，`POLLERR|POLLHUP|POLLNVAL` → 报错断连；不可写则 `return` 交还 worker 循环；
    - `chunk = min(65536, remaining)`，`flags = BINARY|TEXT | CURLWS_OFFSET`，
      `fragsz = header_written ? 0 : total`（首调声明整帧长度并写帧头）；
    - `curl_ws_send(...)`，`offset += sent`（**先推进再判 res**），
      `fragsz>0 && (OK|AGAIN)` 置 `header_written=true`；
    - `CURLE_AGAIN` / `sent==0` → `return` 续写；其余错误 → 报错断连。
- `tm_curl_websocket_client.hpp`：`ws_std_msg` 增 `bool header_written = false`
  （CURLWS_OFFSET 帧头是否已写，跨重试保持）。

## 验证

- LAN 实测（macOS 客户端 ↔ Linux 服务端）：粘贴 ~0.9 MB 图，客户端连续 `[ws-tx] … res=0` 至
  `[ws-tx] large send done: 924687 bytes`；服务端 `update seq=N，… 字节` 正常落库，
  无 `RSV2/RSV3` / `MASK` / `Checksum` 报错、无断连。
- `[ws] SO_SNDBUF=4194304`（macOS 全额授予 4 MB，未被压低）。
- 发送完成后 MoganSTEM CPU 恢复空闲（早期观察到的 100% 系 `cpptools` 误判，非本进程）。
- 小 update（<64 KB）走同一发送路径的单次分支，行为不变。
- 单元/集成测试未新增：该路径依赖真实 libcurl + 网络，沙箱内 `listen EPERM` 无法起本地服务端验证。

## 备注

- 本修复是**缓解**而非根治：`SO_SNDBUF` 上限内（macOS 实测 4 MB）的大帧不再卡；
  **超过缓冲大小的超大附件仍可能触发 `ws_flush` 忙转**。根治需绕开 `curl_ws_send`
  的忙转——自行按 WebSocket 帧格式（帧头 + 4 字节掩码 + XOR 载荷）组帧，用非阻塞
  `send()` + 阻塞式 `poll()` 直接写 socket（由我方完全掌控流控、无忙转），约 100 行，
  待超大附件需求出现时再做。
- 仅影响原生平台（libcurl）；WASM 走浏览器原生 WebSocket，不涉及。
- 调试中临时加在 `tools/loro-server/server.js` 的每秒 `rawIn`/`paused` 诊断已移除（服务端无辜，定位完成）。
