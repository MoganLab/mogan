## 2026/09/07 通用等待弹窗、OCR 异步识别与用户取消

### What(本次改动做了什么)

1. 新增通用等待弹窗 `WaitProgressDialog.qml`（QML，与 `UpdaterProgress.qml`
   同构）：无限转圈 + 已翻译文案 + Cancel 按钮，可 ESC 取消。文案由调用方
   经 `cpp-wait-dialog-open(message)` 传入，OCR 识别、其他魔法粘贴等异步
   任务共用（通用组件，不绑定 OCR）。
2. C++ 侧新增 glue 对 `cpp-wait-dialog-open` / `cpp-wait-dialog-close`
   （`QTMQmlDialog.cpp`，`run_modal_qml_dialog` 非阻塞模态引擎）：打开幂等
   （重复调用 no-op，保留首个文案与回调），关闭经 `host->close()` 同步析构
   （`WA_DeleteOnClose`）。
3. 新增 `WaitDialogBridge`（`QTMQmlDialogBridge.hpp`）：QML 侧 ESC 与
   Cancel 按钮的取消回流桥——`cancel()` 先 `close()` 宿主，再
   `eval_scheme("(wait-dialog-cancelled)")` 把取消请求发回 scheme 侧。
4. 新增通用 scheme 门面 `(utils misc wait-dialog)`（与 `tooltip.scm`、
   `updater.scm` 同层）：`wait-dialog-open`（translate + 注册取消回调）、
   `wait-dialog-close`、`wait-dialog-cancelled`（C++ 回流入口）。等待弹窗
   不绑定任何插件，后续其他异步任务（魔法粘贴等）直接 `use-modules` 复用。
5. OCR 交互识别链路全异步化（改动位于**商业版仓库**的
   `TeXmacs/plugins/ocr/progs/ocr/liii-ocr.scm`；本仓库该文件保持社区占位
   版，运行时被商业版插件覆盖）：md5 缓存命中直接插入（不弹窗、不发网
   络请求）；未命中打开等待弹窗 -> 异步上传 -> 异步识别（`g_http-async-post`
   + poller 驱动回调）-> 关闭弹窗 -> 插入或错误通知。等待弹窗接线仅一行
   `set-ocr-wait-provider! wait-dialog-open wait-dialog-close`（协议隔离
   注入，通用逻辑全部在门面模块）。
6. 取消语义（per-task 闭包标志）：用户 ESC/点取消时，取消请求经 C++ 回流
   scheme，由编排层置本任务的 `cancelled?` 标志；此后上传完成不再发起识别
   请求、识别完成不插入不弹错误通知（用户已放弃），成功结果仍写 md5 缓存
   （静默 OCR 语义，下次粘贴同图秒出）。不中止已在飞的网络请求（结果到达
   后被忽略，仅浪费带宽）。

### Why(为什么这么做)

- **通用逻辑不寄生在 OCR 插件**：等待弹窗是通用能力（不独属 OCR），门面
  （translate/取消路由/glue 包装）独立成 `(utils misc wait-dialog)`，OCR
  插件只做一行注入接线；后续魔法粘贴等直接复用门面，不动 OCR。
- **必须异步化才能弹窗**：原交互链路用同步 `http-post`，阻塞的正是 Qt 主
  线程（GUI 事件循环）——若只在请求前后开关弹窗，`show()` 后的绘制事件无
  法处理（白窗/幽灵窗），转圈动画（QML `RotationAnimation`，事件循环 timer
  驱动）完全冻结。改用已有的异步 HTTP 基础设施（`g_http-async-post` +
  `g_http-poll`，静默识别已在用）后主线程回到事件循环，动画才转得动、轮询
  回调才执行得了。这与更新器下载弹窗踩过的坑同源（见 `cpp_updater_dialog_
  open` 注释：exec 的嵌套事件循环会冻死 delayed 轮询）。
- **取消回流走 `eval_scheme` 而非过程参数**：mogan 的 glue 生成器
  （`build_glue.lua`）类型集合只有 string/int/bool/tree/widget/url 等，不
  支持 procedure 参数，无法把 scheme 回调直接经 glue 传给 C++。按名字调用
  全局函数 `(wait-dialog-cancelled)` 是现成模式（先例：
  `ParagraphFormatBridge` 的 `paragraph-format-commit`）。
- **per-task 闭包标志而非全局标志**：全局 `cancelled?` 存在「取消后立即
  重开」竞态——旧链还在飞时用户再触发 OCR，`open` 重置标志，旧链回调查询
  到 false，新旧两条链并发插入两次。每个任务在自己的闭包作用域持有标志，
  天然免疫串扰。单线程（取消与回调均在 Qt 主线程串行）保证无竞态。
- **取消路径不走 `closeBridge.cancel()`**：它调 `QDialog::done(Rejected)`，
  对 `run_modal_qml_dialog`（show 型）弹窗只 hide 不析构，会泄漏宿主并使
  `QPointer` 悬垂（更新器注释记录过）。`WaitDialogBridge::cancel()` 直接
  `m_host->close()` 同步析构，且不挂宿主 parent（宿主 `destroyed` ->
  `deleteLater`，排队删除保证 `cancel()` 体在 close 后安全执行完）。
- **取消后成功结果仍写缓存**：识别结果本身有效，缓存零成本；用户下次粘贴
  同一图片直接命中秒出，把「取消后又反悔」的代价降为零。错误则不弹通知
  （用户已主动放弃，再弹错误框是打扰）。

### How(怎么做的)

1. `src/Plugins/Qt/qml/WaitProgressDialog.qml`（新增）：
   - `DialogShell` 外壳；取消动作统一入口 `cancelWait()`——`typeof
     waitCancelBridge !== "undefined"` 保护（与 `dialogMessage` 同风格），
     未注入时降级 no-op 而非 JS 报错（症状是「取消无响应」而非弹窗炸掉，
     易诊断）。
   - ESC 经 `onCancel` 覆盖（默认的 `closeBridge.cancel()` 会泄漏，见 Why）；
     Cancel 按钮用 `DialogButtons` 原子组件，文案经 C++ `qt_translate` 注入
     （"Cancel" 字典已有）。
2. `src/Plugins/Qt/QTMQmlDialogBridge.hpp`：新增 `WaitDialogBridge`（不挂
   宿主 parent，`m_host` 用 `QPointer` 双保险）：
   ```cpp
   Q_INVOKABLE void cancel () {
     if (m_host) m_host->close ();                    // 同步析构宿主
     eval_scheme ("(wait-dialog-cancelled)");         // 回流 scheme
   }
   ```
3. `src/Plugins/Qt/QTMQmlDialog.cpp`（声明见 `QTMQmlDialog.hpp`）：
   `cpp_wait_dialog_open` 注入
   `waitCancelBridge`（注意：context property 必须在 `setSource` 前注入，
   漏注入的旧二进制会报 `waitCancelBridge is not defined`）、`dialogMessage`
   （已翻译文案）、`dialogButtons`（已翻译按钮）；宿主 `destroyed` 信号给两
   个 bridge 挂 `deleteLater`。`cpp_wait_dialog_close` 与更新器同款幂等关
   闭。尺寸 420x240（容纳按钮行）。
4. `src/Scheme/L5/glue_qt.lua` + `TeXmacs/progs/prog/glue-symbols.scm`：
   补 `cpp-wait-dialog-open`（string 参数）/ `cpp-wait-dialog-close`（无参）
   的 glue 声明与符号表登记；`src/Plugins/Qt/moganqml.qrc` 注册
   `qml/WaitProgressDialog.qml`。
5. `TeXmacs/progs/utils/misc/wait-dialog.scm`（新增，通用门面，GPL 层）：
   - `wait-dialog-open msg on-cancel`：注册取消回调（`current-cancel-thunk`
     模块级变量，弹窗全局单例 -> 同时仅一个在飞任务，单 thunk 足够；下次
     打开覆盖注册，正常完成后残留无害）+ `cpp-wait-dialog-open (translate
     msg)`；
   - `wait-dialog-close`：`cpp-wait-dialog-close`；
   - `(tm-define (wait-dialog-cancelled))`：C++ `eval_scheme` 的固定回流
     入口（默认 no-op），转发到当前注册的回调。
6. `TeXmacs/plugins/ocr/progs/ocr/liii-ocr.scm`（**商业版仓库改动，本仓库
   不改此文件**；协议隔离架构）：
   - 头部 `(:use (utils misc wait-dialog))`；注入一行
     `set-ocr-wait-provider! wait-dialog-open wait-dialog-close`；
   - 其余既有注入：`set-notify-user-handler!`（错误通知对话框）、
     `set-ocr-auth-provider!`（认证头）、`set-ocr-poll-delayer!`（delayed
     调度）；
   - 编排（goldfish `(liii ocr-impl)`）：`cancelled?` 为 per-task 闭包变量，
     `on-cancel` 置位；`on-upload-either` 已取消则不发识别请求；
     `on-recognize-either` 已取消则成功写缓存静默终止，未取消则关窗后插入
     或通知。
7. `TeXmacs/plugins/lang/dic/en_US/zh_CN.scm`：补通用文案
   `("Processing, please wait..." "正在处理，请稍候...")`。

### 数据流（取消指令从按键到编排层）

```
ESC / Cancel 按钮 (QML)
  -> waitCancelBridge.cancel()                 [Q_INVOKABLE, QML->C++]
  -> m_host->close() + eval_scheme("(wait-dialog-cancelled)")  [C++]
  -> (wait-dialog-cancelled) -> (current-cancel-thunk)         [门面路由]
  -> on-cancel -> (set! cancelled? #t)          [goldfish 编排闭包]
  -> 各异步回调入口守卫拦截（不发识别/不插入/不弹错/成功仍写缓存）
```

正常完成路径不经过回流：编排层回调里 `wait-close`（即 `cpp-wait-dialog-
close`）程序性关闭，不触发 `wait-dialog-cancelled`。

场景清单：
1. 粘贴图片触发 OCR -> 弹窗转圈 -> 结果插入、弹窗关闭；
2. 上传/识别中 ESC -> 弹窗消失，无插入、无错误框；
3. 识别中点「取消」按钮 -> 同上；
4. 取消后等前一次结果写缓存，再粘贴同一图片 -> 秒出（缓存命中，不弹窗）；
5. 断网状态下取消 -> 后续无「网络错误」弹窗；
6. 取消后立即再次粘贴其他图片 -> 新任务正常（旧链不串扰）。
