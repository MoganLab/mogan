## 3 如何测试

### 3.1 复现（修复前）
LiiiSTEM 启动（带文件参数或恢复上次会话的 scratch buffer）时，C++ 在全局环境 `eval_scheme("(buffer-notify-recent …)")`，而该符号是 `tm-files` 模块的私有 `define`，全局不可见：
```
;unbound variable buffer-notify-recent in (buffer-notify-recent ".../no_name_25.tmu")
```
> 注：若 s7 在报「未绑定变量」后计算「did you mean」建议时崩溃（SIGSEGV），会掩盖这条真错误。该 s7 崩溃由独立任务处理，本任务只修底层未绑定变量。

## 5 What
1. 把 `tm-files.scm:328` 的 `buffer-notify-recent` 从模块私有 `(define ...)` 改为 `(tm-define ...)`，使其在全局环境可见。

## 6 Why

`buffer-notify-recent` 是 `tm-files` 模块的私有 `define`，仅在该模块闭包内可见。但 `src/System/Boot/init_texmacs.cpp:927` 在启动期用字符串拼接构造 scheme 代码并 `eval_scheme` 求值：

```cpp
eval_scheme ("(buffer-notify-recent " * b * ")");
```

`eval_scheme` 在**全局顶层环境**求值，那里没有这个绑定 → s7 报「未绑定变量」。

**对照证据**：同文件中其它被 C++ `eval_scheme` 字符串调用的函数——`switch-to-buffer`（init_texmacs.cpp:931）、`load-pdf-buffer`、`save-buffer-save`——全部是 `tm-define`。`tm-define` 经 `define-public-macro`（`tm-define.scm:364 → 352 → 313`）把符号导出到全局，所以它们能被全局求值找到。唯独 `buffer-notify-recent` 误用模块私有 `define`，于是失败。

「切主题」只是触发场景（LiiiSTEM 启动带多个 no_name scratch buffer + 主题初始化，eval 链路里这段代码被求值），并非根因。

## 7 How
最小改动：`(define (buffer-notify-recent name) ...)` → `(tm-define (buffer-notify-recent name) ...)`。

不改 `init_texmacs.cpp:927` 的 `eval_scheme` 调用方式——C++ 用字符串调 scheme 函数是该文件既有模式（931 行 `switch-to-buffer` 同样如此），让 scheme 侧函数全局可见是对齐的做法，而不是反过来把每个 C++ 调用点都换成 import 式的方案。

函数体、同模块内的调用点（386/1044/1077）无需改动——它们本就在同一模块内，`tm-define` 对模块内调用同样有效。
