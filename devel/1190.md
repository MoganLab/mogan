# 1190 升级内置 Goldfish 到 v18.11.22

## 2026-08-09 升级内置 Goldfish 到 v18.11.22

### What
把 `TeXmacs/plugins/goldfish` 内置的 Goldfish 从 18.11.21 升级到 18.11.22，
同步自本地 `~/git/goldfish`（tag v18.11.22，HEAD `e8281d3c`）。

### Why
跟进上游 18.11.22：srfi-13 / liii string 的 `string-join`、`string-replace`、
`string-starts?`、`string-ends?`、`string-prefix?`、`string-suffix?` 获得
C/C++ 原生实现（上游 devel/0102-0105），`string-join` 另有 O(n) 化（0098，
18.11.21 已含）。mogan kernel 的 `string-join`（kernel/library/base.scm）
走 srfi-13，透明受益，无需接线改动。

### How
上游 18.11.21 → 18.11.22 仅 4 个运行时文件变动，逐文件复制即可：
- `src/goldfish.hpp`：`GOLDFISH_VERSION` 改为 `"18.11.22"`；
- `src/liii_string.cpp`：新增 `g_string-join`、`g_string-starts?`、
  `g_string-ends?`、`g_string-replace` 的 C++ 实现，注册自包含在该文件内；
- `goldfish/srfi/srfi-13.scm`、`goldfish/liii/string.scm`：上述函数改为
  `g_*` 直接别名，`string-prefix?`/`string-suffix?` 复用 starts/ends 的
  C 实现。

复制前逐文件核对 mogan 当前副本与上游 v18.11.21 完全一致（无本地补丁），
升级后 4 个文件与上游 v18.11.22 字节一致。`gf fmt` 会把 `goldfish.hpp`
按 mogan clang-format 风格重排（约 70KB 差异），为保持 vendored 副本与
上游字节一致以便后续 diff 核对，未采纳 fmt 对该文件的格式化。

验证：
- `xmake b stem` 通过，`bin/goldfish --version` 输出 18.11.22；
- 上游测试在内置 goldfish 下通过：string-join 37 correct、
  string-replace 57 correct、string-starts? 31 correct、
  string-ends? 120 correct、srfi-13 exit 0；
- mogan 侧 `xmake r list-test` 64 correct、`xmake r print-widgets-test`
  23 correct。

## 2026-08-09 kernel string-starts?/string-ends? 接线 C 实现

### What
`TeXmacs/progs/kernel/library/base.scm` 的 `string-starts?`/`string-ends?`
从 substring + `==` 的 Scheme 实现改为转调 goldfish 原生
`g_string-starts?`/`g_string-ends?`。

### Why
18.11.22 已把这两个函数下沉为 C 实现（`src/liii_string.cpp`，
`std::memcmp` 字节级比较，无 Scheme 堆分配）；kernel 旧实现每次调用都要
截取子串并分配新 string。两者语义一致（非 string 参数报 type-error、
prefix/suffix 更长返回 `#f`），可透明替换。

### How
沿用 list.scm 的接线惯例：保留 `define-public` 包装与 docstring（apidoc
不丢），函数体直接调 `g_string-starts?`/`g_string-ends?`。`g_*` 由
goldfish.hpp 在解释器初始化时注册（`glue_liii_string`），kernel .scm
加载时即可解析，无需额外 import。

### 涉及文件
- `TeXmacs/progs/kernel/library/base.scm`

## 2026-08-09 kernel string-join 转调 g_string-join

### What
`TeXmacs/progs/kernel/library/base.scm` 的 `string-join` 从
`string-concatenate + list-intersperse` 的 Scheme 实现改为转调 goldfish
原生 `g_string-join`。

### Why
18.11.22 已把 srfi-13 `string-join` 下沉为 C 实现（`src/liii_string.cpp`，
两趟扫描、单次分配 O(n)）；旧实现每次调用都要先 intersperse 出一个中间
列表再 concatenate。全仓库调用点（shortcut-edit、apidoc-funcs、
debug-widgets、scheme-tools、text-outline）均只传分隔符字符串、不传
grammar 符号，可透明替换。

### How
沿用 string-starts?/string-ends? 的接线惯例：保留 `provide-public` 包装与
docstring。注意 `g_string-join` 缺省分隔符是 `""`，而 kernel 契约是
`" "`，故缺省分支显式传 `" "`；多出的第三个参数旧实现静默忽略、新实现
按 grammar 解析，但无调用点这么做。错误路径均为报错（非 string 元素/
分隔符由 C 侧抛 type-error），行为兼容。

验证：headless 加载诊断脚本 6 项语义断言（缺省/指定分隔符、空列表、
单元素、空串元素）全部通过；`xmake r list-test` 64 correct、
`xmake r print-widgets-test` 23 correct。

补纯逻辑测试 `kernel/library/base-test.scm`（`xmake r base-test`，
23 correct）：覆盖 string-join 缺省/显式分隔符、infix 语义、空列表、
空串元素、type-error 错误契约，以及 string-starts?/string-ends? 基本
用例。

### 涉及文件
- `TeXmacs/progs/kernel/library/base.scm`
- `TeXmacs/progs/kernel/library/base-test.scm`（新增）

## 2026-08-09 string-join 分隔符改为必传，kernel 直接转调 g_string-join

### What
排查 `TeXmacs/progs` 全部 `string-join` 调用点，确认均显式传分隔符；
kernel `string-join` 去掉可选参数分支，签名改为 `(string-join ss sep)`，
函数体直接 `(g_string-join ss sep)`。

### Why
上一版包装保留了「缺省分隔符 " "」分支（`if (null? opt) ...`），但
progs 内 5 个调用点（shortcut-edit `" "`、apidoc-funcs `"."`/`"/"`、
debug-widgets `"\n"`、scheme-tools `"\n\n"`、text-outline `":"`）
全部显式传分隔符，缺省分支是死代码；去掉后包装变成纯转调。
plugins/goldfish 下的 tm-gnuplot/tm-tikz/tm-quiver 等缺省调用走
goldfish 自己的 srfi-13 string-join（独立解释器进程），不受 kernel
契约影响，不在本次范围。

### How
- `base.scm`：`(string-join ss . opt)` 改 `(string-join ss sep)`，
  直接转调，docstring 更新；
- `base-test.scm`：缺省分隔符用例改为显式 `" "`（改名
  `test-string-join-space-delimiter`），errors 用例新增缺参抛
  `wrong-number-of-args` 的契约断言。

验证：`xmake r base-test` 24 correct、`xmake r list-test` 64 correct、
`xmake r print-widgets-test` 23 correct；`gf fmt --changed-since=main`
无改动。

### 涉及文件

- `TeXmacs/progs/kernel/library/base-test.scm`

## 2026-08-09 progs 内 string-recompose 调用点迁移到 string-join

### What
把 `TeXmacs/progs` 下全部 27 处 `string-recompose` 调用点（含
`text-speech.scm` 注释里的调试代码、`base.scm` 内
`string-recompose-comma` 与 property 格式化两处内部调用）替换为
`string-join`。`string-recompose` 定义本身保留。

### Why
合法输入下两者结果完全等价（空列表、单元素、infix、空串元素一致），
且 progs 内所有调用点都传 string 分隔符、无人依赖
`string-recompose` 接受 char 分隔符的契约；`string-join` 走
`g_string-join` C 实现（两趟扫描、单次分配 O(L)），而
`string-recompose` 每层 `string-append` 拷贝已拼好的尾部，
总工作量 O(n·L)。`cpp-string-recompose`（C++ glue，另一函数）不动；
`string-recompose` 符号保留——char 分隔符是既有公开契约，第三方可能
在用。

### How
sed 批量替换 `(string-recompose ` → `(string-join `；`base.scm`
仅改 246/267 两行内部调用，保留 230 行定义与 235 行自递归。

验证：`xmake r base-test` 24 correct、`xmake r list-test` 64 correct、
`xmake r print-widgets-test` 23 correct；`gf fmt --changed-since=main`
通过（db-menu.scm 一处缩进被 fmt 修正）。

## 2026-08-09 移除 cpp-string-recompose glue

### What
删除 lolly `recompose` 的 scheme glue `cpp-string-recompose`：
`glue_lolly.lua` 声明块、`glue-symbols.scm` 符号表条目；
唯一调用点 `test-convert.scm` 的 `pdf-info` 改用 `string-join`。

### Why
scheme 侧 `string-recompose` 已移除，`cpp-string-recompose` 是同一
功能的 C++ 版绑定（array_string + string → string），`string-join`
（g_string-join）语义完全覆盖（元素与分隔符均为 string 时结果一致），
无需保留重复入口。lolly 库内 C++ `recompose` 函数本身不动（库公开
API，超出本次范围）。

### How
- `src/Scheme/L2/glue_lolly.lua`：删 9 行声明块，重建后 glue_lolly
  生成代码不再注册该符号；
- `glue-symbols.scm`：删符号表条目（该文件不参与 glue 生成，纯清理）；
- `test-convert.scm:444`：`(cpp-string-recompose k "\n")` →
  `(string-join k "\n")`（`k` 来自 `cpp-string-tokenize` + filter，
  元素均为 string，等价）。

验证：`xmake b stem` 通过；headless 求值
`(defined? 'cpp-string-recompose)` → `#f`，
`(defined? 'cpp-string-tokenize)` → `#t`（未误删）；
`xmake r base-test` 24 correct、`xmake r list-test` 64 correct、
`xmake r print-widgets-test` 23 correct。

### 涉及文件
