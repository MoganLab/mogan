# 0780 渲染与编辑器解耦：Stage 1（headless tmu→png 渲染）

## 背景（Why）
目标：一个**无 UI**（不依赖 Qt/ImGui/glfw）的 CLI，用 **mupdf** 把 `.tmu` 文档渲染成图片。先前尝试因「文档宏涉及 `current-window`」而失败。

探索结论（决定方案形态）：
- 渲染管线本就无窗口、无 Qt：`make_raster_image`（`src/Typeset/Boxes/Basic/boxes.cpp`）→ mupdf 后端的 `native_picture`/`picture_renderer`/`save_picture`（`USE_MUPDF_RENDERER` 恒定义）。
- 无窗口排版模板已存在：`edit_main_rep::print_doc`，从不触碰 `concrete_window()`/`apply_changes`/widget 树。
- 真正的阻塞是少数**未加保护的窗口调用**在 headless 抛 `string` 异常（`ASSERT`/`TM_FAILED` 经 `tm_throw`），表象即「宏崩了」。

## 本阶段干了什么（Stage 1，What/How）
在**现有 Qt-headless 二进制**上打通 tmu→PNG，并消除导致崩溃的窗口阻塞点。**不碰构建系统**。

### 1. 渲染通路（复用现有 mupdf 管线，零新渲染器）
- `edit_main_rep::render_to_images(url dest, double zoomf)`（`src/Edit/Editor/edit_main.cpp`）：形态仿 `print_doc`——`typeset_preamble`/`typeset_prepare` + 自建 `new_typesetter`/`::typeset`，对每页 `the_box[0][i]` 调 `make_raster_image`（mupdf）→ PNG。单页直接 `dest`，多页 `out-1.png`/`out-2.png`…。纯虚声明于 `editor.hpp`，实现在 `edit_main_rep`。
- `buffer_render_to_images(url name, url dest, double zoomf)`（`src/Texmacs/Data/new_buffer.cpp`）：用 `get_passive_view` 取**无窗 view** 调上面的 editor 方法（仿 `buffer_export`）。
- Scheme glue `(render-doc-to-png name dest zoom)`（`src/Scheme/Glue/glue_basic.lua`）。

### 2. 消除窗口阻塞点（上次失败的根因）
- `get_current_window_safe()`（`src/Texmacs/Data/new_window.cpp`）：返回 `url_none` 而非断言（仿 `get_current_view_safe`）；新 glue `(current-window-url)`。
- `get_recent_view(name)`（`src/Texmacs/Data/new_view.cpp`）：改用 `get_current_view_safe()`——修复「buffer 已有 view 但无 current view 时」`buffer_export` 抛异常（阻塞点 #3）。
- `switch_to_buffer`（`src/Texmacs/Data/new_view.cpp`）：用 `has_current_window()` 门控，headless 无窗时切到 passive view 直接返回，不再经 `get_current_window()` 抛异常（即每次 `load-buffer` 的崩点，阻塞点 #1/#2）。

### 涉及文件
- `src/Edit/Editor/edit_main.{hpp,cpp}`、`src/Edit/editor.hpp`（`render_to_images`）
- `src/Texmacs/Data/new_buffer.{hpp,cpp}`（`buffer_render_to_images`）
- `src/Texmacs/Data/new_window.{hpp,cpp}`（`get_current_window_safe`）
- `src/Texmacs/Data/new_view.cpp`（`get_recent_view` / `switch_to_buffer` 修复）
- `src/Scheme/Glue/glue_basic.lua`（`render-doc-to-png` / `current-window-url` 绑定）

## 验证
`xmake b stem`（debug）后，macOS 需重签 `.app` 内 Frameworks dylib（`install_name_tool` 会打脏签名）：
```
find build/.../MoganSTEM.app -type f -name '*.dylib' -exec codesign --force --sign - {} \;
codesign --force --sign - build/.../MoganSTEM.app
```
headless 渲染（输出传**绝对路径**避免 concretize 警告）：
```
TEXMACS_PATH=$PWD/TeXmacs MoganSTEM -headless -x \
  '(load-buffer "$TEXMACS_PATH/tests/tm/38_6.tm") (render-doc-to-png "$TEXMACS_PATH/tests/tm/38_6.tm" "/abs/out.png" 2.0) (quit-TeXmacs)'
```
产出非空 PNG（可见文档内容）；多页文档产出 `out-1.png`/`out-2.png`。

## 已知限制（后续阶段）
- 输出用相对路径时 `Couldn't concretize out.png` 警告（非致命，PNG 仍写出）；CLI 传绝对路径（Stage 3）。
- `page-medium=automatic` 文档仍是默认 10cm 宽；标准 papyrus/paper 不受影响（Stage 3 加 `--width`）。
- 每次 `xmake b` 后需重签 dylib；构建规则修复归 Stage 2。
- 渲染极端尺寸文档可能 OOM（Stage 3 加尺寸上限/分页保护）。

## 后续
- **Stage 2**：无 UI 构建 `mogan-render`——`cli_gui.cpp`（从 `im_gui.cpp` 派生、去 GLFW）+ 新 `cli_frontend` xmake 分支（排除 Qt/ImGui，留 mupdf/Freetype）+ Qt-free 入口；顺手在构建规则里修 dylib 签名问题。
- **Stage 3**：CLI 打磨（绝对路径、zoom/DPI、多页、错误处理、argv 解析、automatic-medium 尺寸、OOM 保护）。
