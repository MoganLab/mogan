## 5 What

1. 服务端 `sendSyncState` 在补发完 snapshot + updates 后，**总是**追加一个文本帧 `SYNC-END`，作为「同步阶段结束」的确定信号（空文档也发）。
2. 客户端 `on_message` 在 `await_frame` 状态收到 `SYNC-END` 即按空文档 `become_ready`；非空文档首帧到达后已先行就绪，`SYNC-END` 在 `ready` 状态被忽略。
3. 客户端 `poll()` 中 1s 超时兜底放宽为 10s，职责降级为「兼容不发 `SYNC-END` 的旧服务端 / 防连接静默失效」，正常路径不应命中。
4. 文档（README 协议表/时序图、hpp 注释）与服务端单测同步更新。

## 6 Why

`collab_session::poll()` 原有一段 1s 超时：JOIN 后若 1s 内没收到首条二进制历史帧，就按「空文档」`become_ready`。

经探索确认，服务端对**空文档**（无 `snapshot.bin`、无 `updates.log`）**不发任何二进制帧**，所以这个超时是专门为空文档设计的兜底。但它存在真实竞态：JOIN 一个**非空**文档时，若 snapshot 到达慢于 1s（弱网 / 大文档 / 延迟模拟），超时会先在**空编辑器**上 `become_ready`——此刻 `collab_enable()` 已开启本地广播、而 `loro_vv_initialized` 仍为 false，于是开出一个窗口：用户在该窗口内的本地编辑会被 seed 进空 shadow，待真 snapshot 到达时按 `ready` 分支与真文档做 CRDT 合并。

**根因**：客户端无法区分「空文档（无帧）」和「帧还没到」，只能用超时去猜「空」。而 snapshot 与 delta update 在线格式上**不可区分**（`apply_remote` 对二者完全同构，仅靠 `loro_vv_initialized` 一次性抑制回传），无法靠客户端识别帧类型来补救，只能由服务端补一个确定信号。

## 7 How

用服务端的**确定性同步完成标记**取代超时猜测。WebSocket 保证同连接有序到达，故状态推进无歧义：

- 非空文档：`DOC` → snapshot(二进制, `await_frame→ready`) → updates(二进制, ready) → `SYNC-END`(ready, 忽略)
- 空文档：`DOC` → `SYNC-END`(`await_frame→ready`，不再等 1s)
- CREATE 流程：收到 `DOC` 即 `become_ready`，`SYNC-END` 到达时已在 `ready`，忽略——无需改动

未改动部分（已确认无需动）：`apply_remote` / shadow / Rust FFI（snapshot 与 update 同构，首帧到达后内容能正确落地）；CREATE 流程；重连 / 广播 / buffer 关闭逻辑。

保留（而非删除）超时的考量：兼容不发 `SYNC-END` 的旧服务端，并作为连接静默失效的死链兜底；阈值放宽到 10s 避免对正常慢帧误判。若确认服务端与客户端始终同版本部署，可进一步删除该超时，改由 WS 断线 → `on_disconnect` → `schedule_reconnect` 兜底。
