## 3 如何测试

### 3.1 确定性测试（单元测试与语法检查）
```bash
xmake b stem && xmake r 70_7
```

### 3.2 非确定性测试（交互验证）
1. 在 Windows 平台启动 Mogan STEM：`xmake r stem`；
2. 在首页（欢迎界面）的「最近的文档」列表中点击打开 `1319.tmu`（只能通过首页来测试复现）；
3. **预期结果**：
   - 包含 Python session 的文档能正常加载并显示渲染，不会发生软件卡死（stuck）或无响应错误。

## 4 What
1. 初次打开文档时会加载相应插件。如果文档本身使用了特定语言插件（如包含 Python session/code 的文档），在 `prog-mode.scm` 尚未被系统加载的情况下，加载 `xxx-edit.scm` 会因为 `in-prog-xxx?` 等符号没有定义而报错，导致软件卡死；
2. 参考 `lua-mode.scm`、`scala-mode.scm` 等独立语言模式设计，统一为所有语言插件建立专属的 `*-mode.scm` 与 `*-edit.scm`；
3. 将 `prog-mode.scm` 集中定义的各个具体编程语言模式（`cpp`、`java`、`javascript`、`json`、`python`、`julia`）解耦拆分至各自插件目录下；
4. 将 `goldfish` 与 `r7rs` 中内联在 edit 中的 `texmacs-modes` 拆分至专属 mode 模块；
5. `scheme-edit.scm` 显式加载 `(code prog-mode)`；
6. 为 `javascript`、`json`、`julia` 补齐 `*-edit.scm` 并在各自 `.stem` 中统一通过 `*-edit` 加载对应 mode；
7. 清理已废弃无引用的 `dot` 和 `fortran` 模式定义；
8. `prog-mode.scm` 仅保留 `(in-scheme% ...)` 和 `(in-prog-scheme% ...)`。

## 5 Why
1. 修复由于符号未定义引起的卡死 Bug：在首页启动阶段，`prog-mode.scm` 尚未被加载；如果此时直接从首页最近文档打开带有某语言插件的文档，该语言的 `xxx-edit.scm` 中注册的 `(:mode in-prog-xxx?)` 槽和快捷键便会遇到未定义符号，引发软件卡死；
2. 模块自包含与解耦：每个语言插件应该自行管理其语法模式与谓词，不应隐式依赖外部公共模式文件的加载时序；
3. 架构统一规范：所有编程语言插件均遵循 `(<lang> <lang>-mode)` -> `(<lang> <lang>-edit)` 的自包含模式加载链。

## 6 How
1. 创建 `python-mode.scm`、`cpp-mode.scm`、`java-mode.scm`、`javascript-mode.scm`、`json-mode.scm`、`julia-mode.scm`、`goldfish-mode.scm`、`r7rs-mode.scm`，通过 `texmacs-modes` 分别定义对应的 `in-<lang>%` 和 `in-prog-<lang>%`；
2. 在 `python-edit.scm`、`cpp-edit.scm`、`java-edit.scm`、`goldfish-edit.scm`、`r7rs-edit.scm` 的 `:use` 声明中引入各自的 mode 模块；
3. 创建 `javascript-edit.scm`、`json-edit.scm`、`julia-edit.scm` 并在各自的 `.stem` 中引入对应的 edit 模块；
4. 在 `scheme-edit.scm` 的 `:use` 中加入 `(code prog-mode)`；
5. 在 `prog-mode.scm` 中移除上述迁移出的语言及历史无用模式，仅保留 scheme 相关模式。
