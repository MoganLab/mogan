
## 5 What

1. `QTMGuiHelper::eventFilter` 中，将双击文件打开的目标从"第一次事件 vs 之后事件"
   改为"当前是否有可用窗口"决定：有窗口走 `:current-window`（新标签页），没有才
   `:new-window`。
2. 删除 `static bool new_window_flag` 状态机。
3. 新增 GUI 验证脚本 `TeXmacs/tests/2020.scm`。

## 6 Why

在 OS 文件管理器里双击 `.tmu` 文档，期望像浏览器那样在**已有窗口**里新开标签页，
而不是每双击一次弹一个新窗口（除非当前没有任何窗口）。

原实现用 `static bool new_window_flag`：第一个 `QFileOpenEvent` 用 `:current-window`，
之后所有事件一律 `:new-window`。判断标准是"是不是第一次事件"——这恰恰搞反了：第二次
双击时明明已有现成窗口，却开了新窗口。正确的判断标准应是**当前有没有可用窗口**。

## 7 How

### 7.1 判断标准改为窗口存在性

```cpp
const char* win = has_current_window () ? ":current-window" : ":new-window";
```

- `:current-window` → `load-buffer-open` 走 `switch-to-buffer`，在当前窗口新开标签页。
- `:new-window` → `open-buffer-in-window`，创建新窗口（仅无窗口时兜底）。

`has_current_window()`（`new_window.cpp`）检查当前 view 是否绑定了真实窗口，比
`get_nr_windows() > 0` 更精确——确保有可用、能接收新标签页的当前窗口。

### 7.2 冷启动首文件不会开双窗口

关键时序保证：`ensure_window()`（`init_texmacs.cpp:904`）在 `gui_start_loop()`（事件循环，
`:973`）**之前同步**执行。`QFileOpenEvent` 只有进入事件循环后才派发到 `eventFilter`，
故处理时窗口必然已存在，`has_current_window()` 为真。因此即使从冷启动（双击文件唤起
Mogan），第一个文件也会走 `:current-window`，在欢迎窗口里以标签页打开（并按
`load-buffer-open` 既有逻辑关掉未修改的欢迎 scratch buffer），不会出现"欢迎窗口 +
新文件窗口"的双窗口。

### 7.3 GUI 测试为何不直接复现双击

`QFileOpenEvent` 由 OS（macOS Cocoa 层等）在启动时派发，Scheme 测试进程内无法真实
注入该事件。强行 mock 等于测 mock 自身。故 `2020.scm` 转而断言修复所依赖的下游契约
（默认路径开标签页、`:new-window` 才开窗），并用 `:new-window` 步作对照组。C++ 门控
本身留给 3.2 的人工双击实测。

### 7.4 验证

`MOGAN_TEST_GUI=1 xmake r 2020` 全部 `[2020-check]` 断言 OK：默认路径窗口数恒为 1，
显式 `:new-window` 窗口数变为 2。

## 8 Linux 单实例 IPC（本轮补丁）

### 8.1 问题：`QFileOpenEvent` 在 Linux 上不触发

7.3 节的修复依赖 `QFileOpenEvent`，但该事件**只在 macOS** 上由 Qt 派发（Cocoa 层
`application:openFile:`）。Linux（X11/Wayland）上：

1. `TeXmacs/misc/mime/MoganSTEM.desktop` 用 `Exec=moganstem %U`，**无单实例封装**，
   每次双击 `.tmu` 都启动一个**全新进程**，文件作为位置参数传入 `argv`。
2. `QFileOpenEvent` 在 Linux 上根本不触发，故 7.1 的 `eventFilter` 改动对 Linux 是
   空操作——双击仍走 `init_texmacs.cpp` 的 `TeXmacs_main` 命令行首文件分支，永远
   命中 `first_file==true` → `new_buffer_in_this_window` → **永远弹新窗口**。
3. 更糟的是 crash：新进程执行 `init_texmacs()` → `acquire_boot_lock()`
   （`init_texmacs.cpp`），发现已有实例留下的 `boot_lock`，于是**删除正在运行实例的
   `settings.scm`、整个 tm 缓存、字体错误日志**。两个进程抢这些共享文件 → 后开的
   进程（或前一个）崩溃。

### 8.2 方案：`QLocalServer`/`QLocalSocket` 单实例

新增 `src/Plugins/Qt/QTMSingleInstance.hpp`/`.cpp`（`#if defined(Q_OS_LINUX)`）：

- 客户端 `mogan_forward_to_running_instance(argc, argv)`：在 `research.cpp` 的
  `main()` 里 QApplication 构造之后、`init_texmacs()` 之前调用。用 `QLocalSocket`
  连 `$TEXMACS_HOME_PATH/system/mogan_socket`；连得上就把 argv 中的位置参数文件
  （绝对路径，`url_pwd()` 解析）逐行发过去，等一个字节 ACK，返回 true → 调用方
  `return 0` 退出，**不进 `init_texmacs()`、不碰 boot_lock**。连不上（无实例）返回
  false，正常启动。
- 服务端 `mogan_start_single_instance_server()`：在 `init_texmacs.cpp` 的
  `TeXmacs_main` 里 `gui_open`/`ensure_window` 之后调用（此时 scheme 已起、窗口已建）。
  `QLocalServer::listen` 监听同一 socket，收到连接读出路径，用
  `exec_delayed(scheme_cmd(load-buffer ... :current-window))` 在当前窗口开新标签页，
  回 ACK。

macOS 维持 `QFileOpenEvent` 路径。Windows 与 Linux 共用本模块（`QLocalServer`/`QLocalSocket`
在两者均为 Qt 原生：Linux 走 Unix domain socket，Windows 走命名管道）。Windows 上的 socket
"路径"是一个固定短名 `moganstem-single-instance`——`QLocalServer` 在 Windows 上忽略路径、
只用 name 作为 `\\.\pipe\<name>` 的管道名（路径分隔符在管道名里非法）。多账号隔离由 Windows
命名管道的会话命名空间自动提供（不同登录会话看不到彼此的 `\\.\pipe\`）。

### 8.3 豁免：headless 与批处理

转发/监听都必须豁免以下场景，否则会破坏测试与 CLI：

- **headless**：`research.cpp` 的转发受 `!headless_mode` 门控；`init_texmacs.cpp` 的
  服务端注册同样受 `!headless_mode` 门控。否则 headless 测试进程会抢走桌面 GUI 实例
  的 socket（`QLocalServer::removeServer` 会删掉对方的监听文件），或被转发吞掉。
- **批处理/转换**：`research.cpp` 里新增 `argv_has_batch_options()` 检测
  `-c/-convert/-q/-quit/-x/-execute/-build-manual/-reference-suite/-test-suite`，
  命中则放行（这些是显式 CLI 任务，不属于双击语义）。
- **无文件**：argv 没有位置参数文件时不转发，否则"再开一次"会被静默吞掉。

### 8.4 协议与并发加固（本轮补丁）

review 提出的健壮性问题已修复：

- **协议改为 EOF 驱动、去掉 ACK**：原协议"客户端发完等 ACK、服务端等 disconnected 才发
  ACK"在异步改造后形成死锁——客户端不主动断开（等 ACK），服务端的 `disconnected` 信号
  永远不触发，最终两边都靠超时退出。新协议：客户端把所有路径逐行写完后 `flush()` +
  `waitForBytesWritten()`，立即 `disconnectFromServer()`；服务端以"读到 EOF"（客户端
  关闭连接）作为一条完整消息的边界，处理完即清理。ACK 在此场景下冗余——客户端进程
  本来就要退出，无需服务端确认。
- **服务端全程不阻塞 GUI 主线程**：`handle_connection` 信号回调、`read_from_client`、
  `discard_client` 三处都不调用任何 `waitFor*`。原 `disconnected` 回调里的
  `waitForDisconnected(1000)` 也已删除——进入该回调说明已断开，再等是多余的，反而阻塞
  事件循环 1 秒。
- **读取跨片到达**：累加缓冲 `QByteArray`，每次 `readyRead` 追加、按 `\n` 切行处理、
  最后一个不完整行留到下次；`read_from_client` 处理完所有完整行后，若缓冲已空且 socket
  已 `UnconnectedState`，立即 `discard_client`（无需等 `disconnected` 信号）。
- **兜底定时器用 `startTimer`/`timerEvent` 而非 `QTimer::singleShot`**：`discard` 时
  `killTimer`，避免悬挂连接清理后定时器仍空触发 lambda。
- **路径含 `\n` 加固**：客户端 `collect_files_to_open` 检测到路径含换行符就跳过该路径
  ——发过去会破坏消息边界。跳过的路径走本地启动旧路径打开该文件，而不是默默吞掉。
