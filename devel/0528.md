## 2026/09/14 「帮助 -> 检查更新」重构与平台分流交互

### What（本次改动做了什么）

1. **菜单与功能重命名**：
   - 将「帮助」菜单中的「版本」（`Version`）重命名为「检查更新」（`Check for updates`），动作绑定为 `(check-for-updates)`，兼容保留 `(mogan-version)` 转调。
2. **废弃静态 `.tm` 文件，改用后端 `/latest` JSON 接口**：
   - 彻底移除对 `https://liiistem.cn/*_latest_version.tm` 的静态文件依赖与 `extract-version-from-tm-content` 正则解析；
   - 社区版与商业版分别请求后端公开的 `/latest` 接口（`https://liiistem.cn/api/v1/public/update/win-x64/latest` 及 `/commercial/...`），通过项目内置 `(liii json)` 解析 `data.version`；
   - 社区版与商业版分别仅展示各自的当前版本与最新稳定版。
3. **平台差异化交互分流**：
   - **Linux 平台**：
     - 主按钮显示为【前往下载】；
     - 当前已是最新版本时，主按钮处于禁用状态（置灰不可点击）；
     - 存在新版本时，点击唤起系统默认浏览器打开官网下载页面。
   - **Windows / macOS 平台**：
     - 主按钮显示为【立即更新】；
     - 当前已是最新版本时，主按钮处于禁用状态（置灰不可点击）；
     - 存在新版本时，点击触发 Velopack 客户端更新流程（复用 `updater.scm` 的下载中间态弹窗与就绪后重启提醒）。
   - **双按钮设计与退出**：
     - 右侧提供【关闭】按钮，支持鼠标点击退出；
     - 支持按键盘 `ESC` 键关闭弹窗。
4. **QML & C++ Bridge 改造**：
   - `DialogButtons.qml` 支持 `primaryEnabled` 属性控制主按钮的禁用态（置灰、不可点击、光标为标准箭头）；
   - `VersionDialogBridge` 暴露 `primaryEnabled` 属性给 QML，并支持自定义主按钮与关闭按钮文案；
   - `cpp_version_dialog` 增加主按钮标签与是否启用的参数传递。
5. **`updater.scm` 新增公开的一键更新入口**：
   - 新增 `(updater-trigger-manual-update)`，作为「检查到新版本后立即更新」的唯一公开入口，供版本弹窗的【立即更新】按钮调用；
   - 内部由 `updater-manual-update-poll` 轮询驱动既有状态机：就绪态（4）询问是否重启、下载/校验中（1/2/3/5）持续等待、无新版本（0）提示已是最新、失败（6）走失败通知，并设 600 次轮询上限超时兜底；
   - 该入口以 `(use-plugin-updater?)` 为前置条件，未接入 Velopack 的平台（Linux）调用为空操作，由调用方改为跳转官网下载页。

### Why（为什么这么做）

1. **统一版本真相来源**：原先每次发布新版本需人工手动维护服务端静态 `.tm` 文件，极易遗漏且缺乏自动化。后端已有针对 CI/CD 自动同步的 Velopack 发布元数据与 `/latest` 接口，全平台发布版本号保持一致，客户端应直接使用后端公开接口。
2. **契合平台分发特点**：Windows 与 macOS 支持基于 Velopack 的免安装就地静默更新与重启应用，用户期望点击即可自动更新；而 Linux 采用发行版包管理（deb/AppImage/rpm等），不支持静默热更新，更符合预期的是明确引导用户前往官网下载安装包。
3. **优化用户交互心理模型**：当已经是最新版本时，将【立即更新】/【前往下载】显式置灰禁用，并配合【关闭】按钮，比单纯弹出一个告知框更具现代化软件的交互确定感。

### How（怎么做的）

1. **QML 禁用态支持**：
   在 `DialogButtons.qml` 中增加 `property bool primaryEnabled: true`，在主按钮的 `Rectangle` 与 `MouseArea` 绑定中判定 `isBtnEnabled = !primary || row.primaryEnabled`，禁用时半透明无动画无点击反馈。
2. **Bridge 数据流扩展**：
   `VersionDialogBridge` 构造函数新增接收 `primary_button_label`, `cancel_button_label`, `primary_enabled`，并通过 `Q_PROPERTY` 提供只读属性；QML 侧 `DialogButtons` 挂接对应回调与状态。
3. **Scheme 逻辑重构**：
   - `fetch-latest-version` 引入 `(liii json)`，从接口返回结果中安全提取 `version` 字段；
   - 根据平台能力 `(use-plugin-updater?)` 决定按钮文案为 `"Update Now"` 还是 `"Go to Download"`；
   - 比对当前版本与最新版本，决定 `primary-enabled?`；
   - 触发主操作时，按平台分流到 `open-url` 或 `(updater-trigger-manual-update)`。

### 如何测试

1. **C++ 单元测试**：
   ```bash
   xmake b qml_load_test && xmake r qml_load_test
   ```
2. **Scheme 单元测试**：
   ```bash
   xmake b stem && xmake r 2080
   xmake b stem && xmake r 0528
   ```
3. **GUI 功能测试**：
   - Linux 环境下启动 Mogan STEM，点击「帮助」->「检查更新」：
     - 观察弹窗显示当前版本、最新稳定版与状态说明；
     - 若版本为最新，确认【前往下载】按钮处于置灰禁用态，点击无效；点击【关闭】或按 ESC 可正常退出；
     - 模拟低版本时，确认【前往下载】高亮可用，点击能正常在浏览器打开官网。

## 2026/09/14 修复版本号新旧检测逻辑（复用 SemVer 2.0 比对）

### What（本次改动做了什么）

1. **复用 SemVer 2.0.0 解析与比较模块**：
   - 不再在本分支自带一份 `utils/misc/semver.scm` 实现，改为直接使用 main 已集成的 goldfish 模块 `(liii semver)`
     （`TeXmacs/plugins/goldfish/goldfish/liii/semver.scm`，随 goldfish v18.11.34 升级引入）；
   - 该模块提供 `semver-clean`、`semver-parse`、`semver-valid?`、`semver-compare` 及 `semver>?`/`semver<?`/`semver=?`/`semver>=?`/`semver<=?`，严格遵循 SemVer 2.0.0 规范比较优先级：
     - 剥离 build metadata（如 `+build.1`），不参与优先级比对；
     - 核心段（core）按点号分割数值比较；
     - 核心段相等时，普通版本优先级高于预发布（prerelease）版本（如 `2026.3.2 > 2026.3.2-rc.1`）；
     - 预发布标识符逐段比对：纯数字标识符数值比较（如 `rc.10 > rc.2`），纯数字低于非纯数字标识符，非纯数字按 ASCII 字典序比较，标识符数量较多者优先；
     - 容错剥离前缀 `v`/`V` 与空白字符。
2. **修复「检查更新」的版本比对逻辑**（`TeXmacs/progs/doc/help-funcs.scm`）：
   - 废弃原先 `(== cur-ver latest-ver)` 简单字符串不等即判为发现新版本的错误逻辑（该错误会导致本地新版本如 `2026.3.5` 检查时误将远端较旧版本如 `2026.3.2-rc.1` 判定为“发现新版本可用”）；
   - 改为按照 SemVer 比较：仅当 `(semver>? latest-ver cur-ver)` 时才判定发现新版本并启用主按钮；当 `latest-ver <= cur-ver` 时判定为当前已是最新版本并禁用主按钮。
3. **补充单元测试**：
   - 在 `TeXmacs/tests/0528.scm` 中增加针对 `calc-update-status` 的测试，明确锁定 `2026.3.2-rc.1` 绝不比 `2026.3.5` 新。

### Why（为什么这么做）

原先代码使用字符串相等 `(== cur-ver latest-ver)` 判定是否最新，当本地客户端为较新的开发/发布版本（如 `2026.3.5`），而线上最新稳定版或预发布版本为较低版本（如 `2026.3.2-rc.1`）时，字符串不相等导致误判为“发现新版本可用”，且主按钮亮起允许更新/下载。按照 SemVer 2.0.0 规范，只有远端版本严格高于本地版本时才应提示更新。

SemVer 模块本身已作为独立提交（goldfish `(liii semver)`）引入，本分支（检查更新重构）不再重复携带一份本地实现，避免两份实现并行演化导致行为漂移。

### How（怎么做的）

1. `help-funcs.scm` 引入 `(liii semver)`（无 C++ 绑定依赖），提取 `calc-update-status` 函数通过 `semver>?` 精确判定新旧；
2. `fetch-latest-version` 提取版本号时通过 `semver-clean` 统一清洗。

```bash

```

## 2026/09/16 修复手动更新入口的 arity 报错 + 禁用通道下主按钮恒置灰

### What（本次改动做了什么）

1. **修复 `updater-question` 的两处错误调用（`updater.scm`）**：
   - `updater-manual-update-poll`（st==4 分支）与 `updater-trigger-manual-update`（st==4 分支）各传了 2 个实参，而
     `updater-question` 是单参 `define`，实参多一个 `(translate "Restart")`——调用即抛 `wrong-number-of-args`；
   - 删掉这两处多余的第二个实参，6 个调用点恢复一致。

2. **禁用通道下「检查更新」弹窗主按钮恒不可用（`help-funcs.scm`）**：
   - 新增 `updates-disabled?`：更新器平台且 `update-channel == "disabled"` 时为真；非更新器平台（Linux）
     恒为假；
   - 新增 `calc-primary-enabled has-new? disabled?`：仅有新版本**且**未禁用时才可用；
   - `check-for-updates` 用二者重算 `primary-enabled?`，并在动作前再判一次该标志，禁用通道下不触发
     `updater-trigger-manual-update`；
   - 新增状态文案 `Automatic updates are disabled.`（禁用通道优先于版本状态显示）；
   - 顺带把 `calc-update-status` 三元组第三项由 `primary-enabled?` 更名 `has-new?`——它只表达版本维度，
     按钮可用性已上移到 `calc-primary-enabled`，避免同名两义。

3. **补测试（`TeXmacs/tests/0528.scm`）**：
   - `test-updates-disabled-predicate`：断言 `updates-disabled?` 的通道契约；
   - `test-primary-enabled-gate`：锁定「有新版本 + 禁用通道 ⇒ 置灰」的真值表；
   - `test-disabled-channel-smoke`：禁用通道下走一遍 `check-for-updates`，保证新增的取通道调用路径不报错。

### Why（为什么这么做）

1. **arity 报错会让手动更新静默失效**。`updater-question` 的签名在本次重构中由 `(message ok-label)` 收窄为
   `(message)`（按钮统一为 Cancel/OK），切换通道那几处调用点都改了，但新写的两个 st==4 分支照抄了重构前的
   文本。后果：用户在 READY 状态走到这两条路径时，`updater-question` 直接抛错——
   `updater-manual-update-poll` 已先关掉下载进度弹窗，于是**进度弹窗消失、重启询问不出现、也不 apply**；
   `updater-trigger-manual-update` 则是点了【立即更新】什么都不发生。更新本身不丢（Velopack 下次启动会
   自动应用），但交互是断的。
2. **禁用通道下按钮可点会破坏「禁用自动更新」的承诺**。`disabled` 只挡了启动链路（`init-research.scm`），
   而【立即更新】走的是 `updater-trigger-manual-update`，其中 `(when (or (== st 0) (== st 6))
   (updater-check-background))` 会重新发起检查并下载——等于绕过禁用语义。把按钮恒置灰后，这条路径不再
   可达，承诺自洽；用户要更新须回首选项把通道切回 stable/beta（该切换本身走既有确认链，可用）。
3. **置灰不能只靠 Qt 侧**。测试钩子 `MOGAN_TEST_VERSION_DIALOG=ok` 会绕过按钮直接返回 `#t`，
   故在 Scheme 侧再判一次 `primary-enabled?`，不依赖单点防护。

### How（怎么做的）

1. `updater.scm` 两处删掉 `(translate "Restart")`。提示语「The update is ready. Restart now to apply it?」本身
   已表达动作，确认键用统一的 OK 不影响语义（与 `updater-switch-chain-poll` 一致）。
2. `updates-disabled?` 必须先判 `use-plugin-updater?`——非更新器平台不加载 `(utils misc updater)`，
   `updater-current-channel` 未绑定，靠 `and` 短路规避。
3. `check-for-updates`：`primary-enabled?` 改为 `(calc-primary-enabled (caddr status) disabled?)`；
   `status-line` 的 `cond` 把 `disabled?` 放首位；动作处嵌套 `(when primary-enabled? ...)`。
4. 新文案 `Automatic updates are disabled.` 加入 `zh_CN.scm`。

### 已知未覆盖

- **st==4 两条路径无法单测**：需要真实的「已下载就绪」状态，`tm_velopack` 没有状态注入钩子，构造不出来。
  本次仅按调用点逐一核对参数个数。
- **「有新版本 + 禁用通道」的端到端组合未跑通**：本机 `xmacs-version` 与线上 latest 均为 `2026.3.5`，
  `has-new?` 恒为假，无法与「无新版本」区分；且实测 `tm-define` 无法覆盖 glue 函数
  `cpp-version-dialog`，捕获不到传入的 `primary_enabled`。该组合由 `test-primary-enabled-gate` 的真值表
  覆盖（这也正是把判定抽成纯函数的原因），端到端需等真实的 rc/发布周期验证。

## 2026/09/16 「检查更新」弹窗感知更新通道（stable/beta）

### What（本次改动做了什么）

1. **新增 `latest-version-channel`（`help-funcs.scm`）**：返回本次展示应取用的通道，
   归一规则与 C++ `tm_velopack::update_channel()` 逐字对齐——只有 `"beta"` 归 `"beta"`，
   其余（含 `"disabled"`/未设/脏值）一律归 `"stable"`；非更新器平台恒 `"stable"`。
2. **`get-latest-version-url` 增加 `channel` 形参**：请求带上 `?channel=<stable|beta>`，
   社区版/商业版两条路径都带。
3. **`check-for-updates` 按通道取版本并展示**：`latest-ver` 由该通道的 `/latest` 取得；
   版本文案随之切换为 `Mogan STEM latest beta version: v%1` / `Liii STEM latest beta
   version: v%1`（stable 沿用原文案）。
4. **`zh_CN.scm` 补两条 beta 版本文案**，措辞与既有「测试版（Beta）」一致。
5. **补测试（`TeXmacs/tests/0528.scm`）**：`test-update-urls` 改为按通道断言 URL 拼接
   （含 beta 用例）；新增 `test-latest-version-channel` 锁定归一规则。

### Why（为什么这么做）

改动前，弹窗的「最新版本」与按钮的动作是两个互不知情的真相来源：版号取自**不带通道
参数**的 `/latest`（等价于 stable），而【立即更新】按钮走的是 `updater-trigger-manual-update`
→ 后台更新器，按**首选项里的当前通道**取包。beta 渠道下二者会直接矛盾——弹窗上写着
「当前已是最新版本」（其实比的是 stable），按钮却亮着，点下去拉的是 beta 包并可能
**降级**（C++ 侧 `AllowVersionDowngrade=true`）。展示与动作必须同源。

### How（怎么做的）

1. 归一规则不在 Scheme 里另立一套，而是照抄 C++ 那一条：`"beta"` 之外全部落到
   `"stable"`。`disabled` 不是真实 feed 通道，归一到 stable 既避开未定义行为，也与
   「禁用时仍展示 stable 版号、重新启用后拿到的就是它」的语义自洽。
2. `check-for-updates` 里 `channel` 只算一次，URL 与版本文案共用同一个值，杜绝两处
   各自判断又漂移。
3. 版本文案跟通道走的原因：beta 通道的版号可能是 `-rc` 预发布，此时标成
   "latest stable version" 就是事实错误。

### 已知问题：staging 的 beta 渠道为空时弹窗会误报失败

实测 `test.liiistem.cn` 的 `releases.beta.json` 目前有 0 个版本（stable 有 3 个），
该渠道的 `/latest?channel=beta` 返回 HTTP 200 但 body 是
`{"code":404,...,"data":"暂无已发布版本","success":false}`。`fetch-latest-version` 把
「该渠道暂无已发布版本」与真正的请求失败都收敛成 `""`，于是 staging + beta 下弹窗显示
「检查更新失败。」——**相对改动前是行为回归**（改动前不带通道参数，staging+beta 用户拿到
的是 stable 的版号，能正常展示）。

建议后续把两者区分开：`data` 为字符串（业务侧「暂无版本」）时展示「该渠道暂无可用版本」
一类的文案，而不是失败。本次未一并做，需要先定文案与产品语义。

### 如何测试

```bash
xmake b stem && xmake r 0528
xmake b stem && xmake r updater-test
```

覆盖情况：URL 拼接（stable/beta × 社区版/商业版）、通道归一（beta/disabled/stable）、
以及既有 semver 与置灰真值表，共 23 项断言。未覆盖：真实 GUI 弹窗文案需手动核对——
把首选项 `update-channel` 切到 beta 后点击「帮助 -> 检查更新」，确认版本行是
「最新测试版（Beta）」而非「最新稳定版」。
