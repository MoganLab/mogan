## 3 如何测试

1. 启动 Mogan STEM。
2. 打开 PDF 文档，框选截图区域 → 终端无 OCR 输出，但后台异步发起识别请求。
3. 等待几秒（识别完成），打开空文档按下 `Ctrl+Shift+v`，预期命中缓存，并在1s内插入 OCR 结果。
4. 重新截一张图，`Ctrl+Shift+v` 触发 OCR，此时等待时间较长。待结果渲染后，再次按下快捷键，预期命中缓存，1s内插入。
5. 重新截一张图，插入文档中，使用悬浮菜单中的 OCR 按钮触发 OCR ，此时等待时间较长。待结果渲染后，再次按下 OCR 按钮，预期命中缓存，1s内插入。

## 5 What
1. 新增 mogan 仓库内的二进制安全 MD5 工具：`src/Mogan/HashUtils/hash_utils.{hpp,cpp}`，基于 `QCryptographicHash`，正确处理含 NUL 字节的 string（mogan 的 `string` 用 `N(s)` 取长度，不依赖 `strlen`）。
2. 通过 `glue_basic.lua` 把 `md5_binary` 暴露为 Scheme glue `md5-binary`，全局可见。
3. `TeXmacs/plugins/ocr/goldfish/liii/ocr-network.scm` 新增异步版本 `upload-base64-async`、`recognize-async`，回调接收 either 包裹的结果。
4. 新建 `(liii ocr-cache)`：全局 hash-table，键为图片 base64 字符串的 MD5，值为后端识别返回的 JSON。
5. 新建 `(liii ocr-poller)`：惰性启动的 100ms 自重排 HTTP poller，用于派发异步回调。
6. 新建 `(liii ocr-silent)`：从剪贴板取 image tree → 算 MD5 → 查缓存 → 未命中则异步上传+识别 → 把识别 JSON 写入缓存。不操作 buffer、不弹窗、不感知成败。
7. `qt_pdf_reader_widget.cpp::finishRectSelect` 在 `clipboard->setPixmap` 后 `exec_delayed(scheme_cmd "(when (defined? 'ocr-recognize-silent) (ocr-recognize-silent))")`。
8. `ocr-impl.scm` 两个老入口（`ocr-to-latex-by-cursor-impl`、`ocr-to-latex-by-image-impl`）开头加缓存查询；识别成功后写缓存。命中分支直接走 `inserter`，与非命中路径共享同一段 `insert-by-cursor` 逻辑。
9. `ocr-render.scm` 移除 `ocr-result->tree` 及 4 个 helper（`latex-result->tree`、`markdown-result->tree`、`html-result->tree`、`list-result->tree`）。缓存改为存 JSON 后，这些 tree 构建函数不再需要——命中路径直接拿 JSON 走 `insert-by-cursor`，逻辑与网络返回路径一致。

## 6 Why
PDF 阅读场景中，用户经常对同一份 PDF 反复截图 OCR。原流程每次都走完整网络往返（上传 + 识别），既慢又消耗后端配额。

引入"静默 OCR"：PDF 截图完成时**主动**把图片识别一次（用户无感知），结果按图片 MD5 缓存。用户后续对同一张图触发正常 OCR 时，直接命中缓存，**无网络请求**、瞬间插入。

之所以缓存 JSON 而非 texmacs tree：
- list format 的识别结果对应多段版面（title + 段落 + 列表 + 公式混合），原本就没有单一 tree 表示——老流程是 `for-each` 逐段 `insert + kbd-return`。
- 缓存 JSON 后，命中路径走**完全相同的** `insert-by-cursor` 处理逻辑，行为与非命中路径一致，避免"命中分支输出格式异常"的整类问题。

之所以需要新的 `md5-binary` glue：goldfish 自带的 `(liii hashlib)` 库 `g_md5` 用 `tb_strlen` 取长度，对含 NUL 字节的二进制 string 在首个 NUL 处截断（实测 `"HI"`、`"HI\0!"`、`"HI\0"` 三个不同字符串 MD5 相同）。goldfish 是独立仓库，修复需走"上游 PR + bump mogan 版本"流程，对一个 OCR 缓存功能来说过重。mogan 自己加 glue 绕开此 bug，是当前任务范围内的最小可行解。

之所以 `md5_binary` 放在独立的 `src/Mogan/HashUtils/` 模块：MD5 是通用工具，不属于任何现有业务模块（`Cache` 是图片缓存、`Telemetry` 是遥测、L5 是 TeXmacs 高级操作）。独立模块便于未来其他场景复用（去重、签名、其他缓存键等）。

## 7 How
**MD5 二进制安全性的实现要点**：mogan 的 `string` 类型本身正确存储 NUL 字节，`N(s)` 返回真实长度。`md5_binary` 用 `QByteArray(as_charp(s), N(s))` 构造输入，绕开 `strlen` 类截断；`QCryptographicHash::hash` 本身二进制安全。返回的 hex 字符串用 `string(hex.constData(), hex.size())` 重新包装为 mogan string。`hash_utils.cpp` 与 `Mogan/Cache` 一致，放在 `qt_frontend` 守卫内编译。

**异步 HTTP 派发机制**：goldfish 的 `(liii http)` 已有 `http-async-post` 与 `http-poll`（C++ 侧 `g_http-async-post`、`g_http-poll`），但当前 codebase 无人调用——OCR 是首个真实用户。`http-async-post` 入队后台请求并立即返回；`http-poll` 在主线程扫描已完成请求、执行 Scheme 回调。`ocr-poller.scm` 用 `(delayed (:pause 100) (poller-step))` 自重排，启动后永不停止（空 poll 开销极低）；首次静默 OCR 时 `ensure-ocr-poller` 启动它。

**缓存键的选择**：键源是 `raw-data` 节点的内容——即 base64 编码的 PNG 字符串。同一份图片数据 base64 编码是确定的，所以 MD5 一致、缓存可命中。理论上 PNG 编码若因 Qt 版本/参数变化而不同，会导致同一张图算出不同 MD5——已知限制，当前场景可接受（同一进程内 Qt 编码稳定）。

**PDF 截图 → Scheme 的触发**：`qt_pdf_reader_widget.cpp::finishRectSelect` 是 PDF 框选截图的完成回调，原本只做 `clipboard->setPixmap`。新增一行 `exec_delayed(scheme_cmd "(when (defined? 'ocr-recognize-silent) ...)")`——`exec_delayed` 是 mogan 已有的 C→Scheme 派发机制（沿 `QTMGuiHelper::eventFilter` 等先例），`when (defined? ...)` 防御 OCR 插件未加载时不报错。

**`image-tree->raw-bytes` 的细节**：剪贴板 image tree 形如 `(image (tuple (raw-data <base64-str> "png") "w" "h" "" ""))`。`raw-data` 节点的 stree 是 `(raw-data <bytes> "png")`，`cdr` 得到 `(<bytes> "png")` 是 list，必须用 `cadr` 才能取到 bytes 字符串本身（曾因返回 list 触发 `md5-binary` 类型错误）。

**缓存值改为 JSON 的设计权衡**：原计划存最终 texmacs tree（方案 A），list format 出现问题后改为存 JSON。所有 format 走同一条 `insert-by-cursor` 路径——非命中路径只是多了一次 `ocr-cache-set!`，命中路径等价于"网络瞬间返回相同 JSON 后走原 insert 逻辑"，行为完全一致。
