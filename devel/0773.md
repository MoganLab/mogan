# [0773] 修复 ImGui Linux 上 Ctrl+滚轮缩放反相

## 1 相关文档

- `CLAUDE.md` - 项目开发规范
- 引入回归的提交 `a8630673a`（PR #3981「[0751] 修复 ImGui 系统快捷键后修饰键卡死、文字输入失效」）

## 2 任务相关的代码文件

- `src/Plugins/ImGui/im_tm_widget.cpp`
  - `glfw_scroll_callback`：按平台分别判定 zoom 修饰键

## 3 背景 / Why

`glfw_scroll_callback` 用 `last_key_mods`（最近一次 `glfw_key_callback` 收到的 GLFW
`mods` 形参）决定滚轮是「缩放」还是「上下滚动」。

在 X11/Linux 上，GLFW 按键事件的 `mods` 形参取自事件发生**之前**的修饰键状态，对
修饰键自身恰好反相（glfw/glfw#1630、ocornut/imgui#6034）：

- 按下 Ctrl → 该按键事件 `mods` 不含 `GLFW_MOD_CONTROL`
- 松开 Ctrl → 该按键事件 `mods` 含 `GLFW_MOD_CONTROL`

由于「按住 Ctrl 滚动」场景下唯一的按键事件就是 Ctrl 的按下/松开，`last_key_mods`
整体反相，表现为：

- 按下 Ctrl 滚动 → 走上下滚动（应为缩放）
- 不按 Ctrl 滚动 → 走缩放（应为滚动）

回归由 `a8630673a` 引入：该提交为修复 macOS 上系统快捷键（截屏等）吞掉修饰键
keyup 导致 `glfwGetKey` 永久卡在 PRESS 的问题，把全平台的 zoom 判定从
`glfwGetKey` 改成了 `last_key_mods`，顺带把本来正常的 Linux 弄反了。

macOS 的 `NSEvent.modifierFlags`、WASM 的 `e.metaKey` 都是事件即时真实状态，
`last_key_mods` 在这两个平台正确；只有 X11 的 `mods` 形参不可靠。ImGui 自带的
`imgui_impl_glfw.cpp`（`ImGui_ImplGlfw_UpdateKeyModifiers`）同样用 `glfwGetKey`
轮询来绕开这个 X11 限制。

## 4 How

在 `glfw_scroll_callback` 按平台分流：

- `OS_MACOS` / `__EMSCRIPTEN__`：继续用 `last_key_mods`（事件级 mods 即时准确，
  且 macOS 需要避开 `glfwGetKey` 的系统快捷键卡死）。
- 其他平台（Linux/X11/Wayland、Windows）：恢复 `glfwGetKey` 轮询实时按键状态，
  不受 X11 `mods` 反相影响。

```cpp
#if defined(OS_MACOS) || defined(__EMSCRIPTEN__)
  bool zoom_mod=
      (self->last_key_mods & (GLFW_MOD_CONTROL | GLFW_MOD_SUPER)) != 0;
#else
  bool zoom_mod= glfwGetKey (w, GLFW_KEY_LEFT_CONTROL) == GLFW_PRESS ||
                 glfwGetKey (w, GLFW_KEY_RIGHT_CONTROL) == GLFW_PRESS ||
                 glfwGetKey (w, GLFW_KEY_LEFT_SUPER) == GLFW_PRESS ||
                 glfwGetKey (w, GLFW_KEY_RIGHT_SUPER) == GLFW_PRESS;
#endif
```

这是 `a8630673a` 之前在 Linux 上验证可用的写法，仅在 macOS/WASM 上保留 #3981 的
事件级 mods 修正。

## 5 如何测试

### 5.1 非确定性测试（手工验证，Linux）

1. `xmake b stem` 构建通过
2. 打开任意文档，在编辑区滚动滚轮：
   - 不按 Ctrl → 上下滚动（修复前会缩放）
   - 按住 Ctrl + 滚轮 → 缩放（修复前会上下滚动）
3. macOS 回归：触发系统快捷键（如截屏 `Cmd+Shift+4` 后取消）后，不按 Ctrl 滚动
   仍为上下滚动、不被误判为缩放。
