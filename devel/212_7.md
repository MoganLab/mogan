# [212_7] 修复 \nu 符号在导出的 pdf 中无法被正常渲染的问题

## 如何测试

1. 新建文档，输入小写希腊字母 `\nu` 。
2. 通过 `文件 -> 导出为 Pdf` 导出 PDF。
3. 打开导出的 PDF，确认 `\nu` 能正常显示。

## 2026/05/07 修复 \nu 符号在导出的 pdf 中无法被正常渲染的问题

### What

修改 `src/Plugins/Pdf/pdf_hummus_renderer.cpp` 中的 `pdf_is_invisible_format_codepoint`：

1. 对 `ch < 256` 的字符码不再按 Herk 编码解释为 Unicode 字符。
2. 仅对 `ch >= 256` 的明确 Unicode/TeXmacs universal code 继续判断是否为 U+200B zero-width space。

### Why

PDF 导出时，`pdf_hummus_renderer_rep::draw(int ch, font_glyphs fn, ...)` 中的 `ch` 已经是传给具体字体的字形编码或槽位值，不一定等同于原始文档字符。

旧逻辑对 `ch < 256` 执行：

```cpp
internal << (char) ch;
herk_to_utf8 (internal);
```

这会把 8-bit 字体槽位按 Herk 编码解释。Herk 编码中 `#17` 会映射到 U+200B zero-width space，因此旧逻辑会跳过 `ch == 0x17` 的绘制。

但在 TeX 数学字体中，`0x17` 可以是小写希腊字母 `\nu` 的字形槽位。结果是 PDF renderer 将本应可见的 `\nu` 误判为不可见字符，直接 `return`，导致导出的 PDF 中 `\nu` 消失。

### How

将不可见字符过滤的语义边界收窄到明确的 Unicode 路径：

```cpp
if (ch < 256) return false;
string internal= "<#" * lolly::data::to_Hex (ch) * ">";
```

这样：

1. `ch < 256` 被视为字体相关槽位，不在 PDF glyph 绘制层做 Herk/U+200B 判断，避免误伤 TeX 数学字体中的 `\nu`。
2. `ch >= 256` 仍构造 `<#...>` 并通过 `herk_to_utf8` 判断是否为 U+200B，保留对真实 Unicode zero-width space 的过滤。
3. 若需要处理 `<nobracket>`、`<nosymbol>` 等结构性占位符，应在更靠近符号语义的上游处理，而不是在 PDF renderer 中按 8-bit 字体槽位猜测。
