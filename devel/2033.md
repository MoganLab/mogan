# [2033] 隐藏 goldfish 与 GLib 同名的全局符号，修复 Linux 桌面启动崩溃

## 1 相关文档
- [dddd.md](dddd.md) - 任务文档模板

## 2 任务相关的代码文件
- `xmake/goldfish.lua` —
  - `libgoldfish` target（纯 C，s7 源码所在）：新增 `add_cflags("-fPIC", "-fvisibility=hidden")`（非 Windows 平台）
  - `goldfish` target（C++）：新增 `add_cxxflags("-fPIC", "-fvisibility=hidden", "-fvisibility-inlines-hidden")`（非 Windows 平台）

## 3 如何测试

### 3.1 确定性测试（符号验证）
```
xmake b goldfish
xmake b stem
# 修复前会列出 g_log / g_hash_table_ref / g_hash_table_size / g_string_append / g_string_copy
nm -D --defined-only build/linux/x86_64/releasedbg/moganstem | grep -E ' g_[a-z]'
# 修复后：无输出（5 个冲突符号全部从 .dynsym 消失）
```

### 3.2 非确定性测试（启动验证）
```
xmake b stem
xmake r stem
```
在会触发 Qt 加载 GTK3 主题插件（`QT_QPA_PLATFORMTHEME` 指向 gnome/qt6ct 等）的 Linux 桌面（如 Fedora/GNOME）上：

1. 修复前：`xmake r stem` 启动即崩（exit 255，实际 SIGSEGV=139），日志停在 `Opening display...` 阶段、`QTMApplication` 构造时；
2. 修复后：正常启动，日志完整走过 `Opening display...` → `Booting TeXmacs kernel functionality` → `Initialization done` → `Forcing delayed loads`，进程稳定存活。

## 4 What
- 给 goldfish 的两个静态库 target（`libgoldfish` / `goldfish`）加 `-fvisibility=hidden`，让 s7 内部与 GLib 同名的全局函数（`g_log` 等）不再进入最终 binary 的动态符号表（`.dynsym`）。
- 零源码改动，仅改构建脚本一个文件；写法对齐项目既有 `xmake/targets/qwkcore.lua`、`qwkwidgets.lua`。

## 5 Why
moganstem 构建成功，但 `xmake r stem` 启动即 SIGSEGV。gdb 堆栈：

```
#0 s7_car(p=0x80)              s7.c
#1 g_log(sc=..., args=0x80)    s7_scheme_inexact.c   ← goldfish/s7 的 Scheme 数学函数 g_log
#2 _g_io_module_get_default()  libgio-2.0.so          ← GLib 自己的 g_log 日志函数调用方
...
#20 libqgtk3.so                                       ← Qt6 的 GTK3 platform theme 插件
#29 QTMApplication::QTMApplication                    src/Plugins/Qt/QTMApplication.hpp:122
```

**根因**：moganstem 经 Qt widgetapp 规则带入 `--export-dynamic` 链接。goldfish 静态链入后，s7 内部有几个全局函数恰好与 GLib 同名（`g_log`、`g_hash_table_ref/size`、`g_string_append/copy`），它们被导出到了 binary 的 `.dynsym`。运行时 Qt 经 `libqgtk3.so` 加载 libgio/libglib，GLib 内部调用自己的 `g_log` 日志函数时，符号解析抢到了 s7 版的 `g_log`（Scheme 数学函数），把 GLib 的参数当成 s7 对象去 `car` 一个无效指针（`0x80`）→ 段错误。

**触发条件**：依赖运行时 Qt 是否加载 GTK3 主题插件（`QT_QPA_PLATFORMTHEME` 指向 gnome/qt6ct 等的桌面，如 Fedora/GNOME）。纯 KDE 或未配置 Qt 主题的极简 WM 不加载 `libqgtk3.so`，可能不崩——但这不代表安全，冲突符号一日存在就是隐患，根治对所有 Linux 桌面都是正确修复。该 bug 是既有的（当前分支相对 main 无 diff），由系统 GLib/GTK + qgtk3 插件被启用而触发暴露。

**为何 `-fvisibility=hidden` 对本项目零风险**（已 `nm`/`readelf` 亲验）：
- s7 的公共 API（`s7_*`，约 408 个声明在 `s7.h`）**本就没有被导出到 `.dynsym`**（`nm -D | grep -cE ' s7_'` = 0），libmogan 通过静态链接引用它们完全不受影响。
- 项目已有同款先例：`QWKCore`/`QWKWidgets` 用同样的 visibility hidden，同一 moganstem binary 内 `nm -D | grep qwk` = 0，证明 hidden 符号既能从 `.dynsym` 消失、又能满足 binary 内部的交叉引用。

## 6 How
- 对静态库 target 加 `-fvisibility=hidden`，编译时把 goldfish 内部符号（含 5 个冲突 `g_*`）标为 hidden。链接进最终可执行文件时，hidden 符号不会进入 `.dynsym`，于是运行时 GLib 的 `g_log` 会解析到 libglib 自己的版本，崩溃消失。
- 关键区别于 qwk 先例：`libgoldfish` 是 `set_languages("c11")` 的纯 C target（s7 源码所在、冲突符号来源），必须用 `add_cflags`（C）而非 `add_cxxflags`（C++）；`goldfish`（C++）才用 `add_cxxflags` 并附带 `-fvisibility-inlines-hidden`。
- 平台范围对齐 qwk：`if not is_plat("windows")`——Windows/MSVC 用 `__declspec` 机制、无此 flag；Linux 必须修、macOS 防御性纳入、wasm 跟随 `else` 分支无害。
