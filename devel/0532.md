# [0532] OAuth 回调链路改造（四）：liiistem:// 自定义协议深链（Windows）

## 背景

承接 [0524]（redirect_uri 提取）、[0525]（端口系统动态分配）、[0526]（state 校验）、
[0529]（回调服务器按需监听与生命周期管理）。这四步都在完善**本地回环 HTTP** 回调通道，
而 [0524]/[0529] 的「后续」中记录了最终方向：把回调通道切换为 `liiistem://` 自定义协议，
由浏览器原生拉起软件。

切换到自定义协议的两个直接动机：

- **环回通道多实例场景脆弱**：虽然端口已改由系统分配（[0525]），但每次登录仍要占一个
  本地监听端口，且依赖杀软/代理不拦截回环请求；[0529] 为此加了 3 秒延迟关闭等容错。
- **协议通道是安装器既有能力**：tauri-installer 安装时已写入
  `HKCU\Software\Classes\liiistem`（见 [0524] 关联一节），浏览器授权后的 302 重定向
  本身即触发协议确认弹窗，官网前端无需提供任何额外按钮。

## 现状（改造前的空白）

搜索确认，运行时侧与深链相关的能力**完全不存在**：

- 无 `QDesktopServices::setUrlHandler`、无 `QDesktopServices::registerUrlHandler`；
- 无 `QLocalServer` / `QLocalSocket`（项目也没有任何单实例机制，多开是常态）；
- 无注册表写入代码（`QSettings` 仅有一处未使用的 include）；
- `liiistem://` 只出现在 `QTMOAuth.cpp` 的注释里，标注为「后续」。

## 改动

本次只做 **Windows 单平台**。macOS（`CFBundleURLTypes` + `QFileOpenEvent`）与
Linux（`.desktop` 的 `x-scheme-handler`）留待后续。

### 1. 运行时补写协议注册（自愈，不抢占）

新增 `src/Plugins/Qt/oauth_deeplink_registry.cpp`，在 `research.cpp` 启动早期调用。

动机不只是「方便开发」：**Velopack 自动更新不会执行安装器**。`register_url_protocol`
只在 tauri-installer 的 `install_latest` 中调用，因此

- 老 NSIS 用户（`packages/windows/research.nsis` 从不写这个键）升级到新版后，
  `HKCU\Software\Classes\liiistem` 永远是空的，深链直接失效；
- 走静默自动更新的用户同样永远不会跑安装器。

运行时补写是老用户迁移的**必经路径**。

判定表（避免与安装器互相顶掉）：

| 当前状态 | 动作 |
|---|---|
| 键不存在 | 写 |
| 缺 `URL Protocol` 空值标记 | 写 |
| `shell\open\command` 指向的 exe 不存在 | 写 |
| 指向的 exe 存在（哪怕路径 ≠ 当前进程） | 不写，只记日志 |

写入字段与安装器 `lib.rs:797-821` 逐项对齐（同样的键名与 `"%1"` 带引号写法），
确保两边谁先谁后都收敛到同一状态。

### 2. 深链接收与实例路由

新增 `src/Plugins/Qt/oauth_deeplink.hpp/.cpp`。

**URL 如何回到发起登录的那个实例**：`state` 的格式已经是
`<instanceId>.<一次性随机数>`（[0526] 引入），`instanceId` 在 `login()` 之前就已生成。
因此回调 URL 天然带着「我是从哪个实例发起的」：

```
新进程（浏览器拉起）
  ├─ 从 argv 认出 liiistem://
  ├─ 从 state 切出 instanceId
  └─ QLocalSocket 连 "LiiiSTEM-URL-<instanceId>"
       ├─ 连上  → 写 URL → disconnect → 进程退出（全程无界面）
       └─ 连不上 → 原实例已退出，本进程照常启动，丢弃这个 URL
```

每个实例在 `QTMOAuth` 构造后按自己的 `m_instanceId` 起一个 `QLocalServer`。多开时
socket 名天然不同，**不需要「主实例」概念，也不改变现有允许多开的策略**。

「连不上」时**不做接手**。曾设计过「新进程自己换 token，避免 code 白作废」，但这条路
结构上走不通：`m_state` 与 PKCE 的 `m_code_verifier` 都只在 `login()` 内生成，
新进程两者皆无——`handleCallback` 会因 `state` 为空直接拒掉，即便不拒，服务端也验不过
`code_verifier`。让用户在新窗口重新登录一次，比把 verifier 落盘去支持接手更简单也更安全。

### 3. Windows 会改写 URL（实测结论）

用临时 scheme + 原生 exe 实测 `%1` 的传递，发现 Windows 对 custom scheme URL
做了规范化：

```
送出:  LiiiSTEM://callback?code=ABC-123&state=inst42.nonceXYZ
收到:  liiistem://callback/?code=ABC-123&state=inst42.nonceXYZ
       ↑ scheme+host 转小写        ↑ query 前多一个 /
```

因此实现中：

- scheme 判定大小写不敏感（`QUrl::scheme()` 本身也会返回小写）；
- 不依赖 `path()` 判断是否回调，只取 `QUrlQuery` 的 `code` / `state`，忽略 host 与 path。

同一轮实测还确认了两点：

- `shell\open\command` 中 `%1` **必须带引号**（安装器现有写法正确）。实测带引号时
  完整送达 `"liiistem://callback/?code=ABC-123&state=..."`；URL 里的 `&` 不会截断参数，
  因为这条路径不经过 `cmd.exe`，无 shell 元字符解释。
- `URL Protocol` 空值标记是**硬性必要**。漏写时 `ShellExecuteW` 直接返回
  `31 (SE_ERR_NOASSOC)`，应用根本不启动；补上后才返回 `42` 并成功拉起。

### 4. QTMOAuth 接入

- 新增私有 `handleDeepLink(const QString& url)`：解析出 `code` / `state` 转
  `QVariantMap`，**复用现有 `handleCallback`**。state 校验、一次性清空、3 秒延迟关闭
  全部沿用，不新增第二套校验逻辑。
- 新增私有 `startUrlRouter()`，按 `m_instanceId` 起 `QLocalServer` 接收转发来的 URL。
- `getRedirectUri()` 改为返回本次登录发起时固化的 `m_redirectUri`（`login()` 中赋值）：
  深链通道下它是 `liiistem://callback`，HTTP 通道下是 `m_reply->callback()`。这样
  授权请求与令牌交换两处必然一致，也不再依赖「服务器是否仍在监听」这一运行时状态。

#### redirect_uri 的选择：探测注册后深链优先

`login()` 只发一个 `redirect_uri`，服务端也只认那一个——**选定哪条通道，就只有哪条能
收到码**，所以「两路并存」在设计上不成立（见下面的取舍）。最终取舍是探测后深链优先：

```
login():
  deep_link_usable() ?  liiistem://callback      ← 浏览器跳深链
                     :  http://127.0.0.1:<port>/callback
```

`login()` 仍照旧尝试环回监听（端口由系统分配），失败也不 `return`——它是深链不可用时
的唯一出路。

代价与前提：**服务端白名单必须先放行 `liiistem://callback`**，否则授权请求会直接被
`invalid redirect_uri` 打回，登录彻底失败（比走 HTTP 更糟）。上线顺序上，白名单要先于
本版发布。

`deep_link_usable()` 是只读探测，要求注册表键齐全且 `shell\open\command` 指向的**正是
本进程**的可执行文件。指向别的 LiiiSTEM 副本时返回 false 退回 HTTP：那个副本未必带得动
本版的路由逻辑（老版本收到 `liiistem://` 只会开个空窗口，登录就此卡死）。

环回通道保留不删。待安装器 / 官网全线切换、真机验证通过后，再用单独一次改动整体退役 HTTP。

### 5. 前台激活

新进程是浏览器拉起的，有权抢前台，但它只是转发器、几毫秒后即退出。老实例收到 URL 时
前台焦点仍在浏览器上，而 Windows 默认拒绝对非前台进程的 `SetForegroundWindow`，
结果是浏览器亮着、软件在后台静默登录完成。交接分两半，都在 `oauth_deeplink.cpp`：

1. 转发进程在连接成功后调 `AllowSetForegroundWindow(ASFW_ANY)` 让出前台权；
2. 目标实例在 `handleDeepLink()` 开头调 `bring_to_front()`：优先挑 `QMainWindow`
   类型的可见顶层窗口（顶层里还混着搜索栏与各种 popup），最小化时先 `showNormal()`，
   再 `activateWindow()`。

使用 `ASFW_ANY` 而非反查 pid（`GetNamedPipeClientProcessId`）换取实现简单，
代价是那几毫秒内任何进程都能抢前台。如需收紧，后续改为按 pid 精确授权。

`AllowSetForegroundWindow` 有前置条件、可能失败。失败不致命（登录照常完成，只是
窗口不弹出来），故只记一条 `debug_boot` 日志而不中断流程——真机上若发现窗口没动静，
日志里能看到是不是卡在这一步。

### 6. 单元测试

新增 `tests/Plugins/Qt/oauth_deeplink_test.cpp`，覆盖纯解析逻辑（xmake 自动发现）：
正常 URL、Windows 规范化后的 `scheme://host/?...` 形态、scheme 大小写、URL-encoded
的 code、参数顺序、`code` 缺失（含 `error=access_denied`）、`state` 缺失、
`state` 段数不对、非 liiistem scheme；`find_url` 跳过 `argv[0]`；`redirect_uri` 稳定。

注册表补写与实例转发要碰真实系统状态（HKCU、本地 socket），不进单元测试，靠下面的
手工验证。

## 验证

- **老用户态**：删除 `HKCU\Software\Classes\liiistem` 后启动，确认键被按当前 exe 路径补上；
- **不抢占**：把键的 `shell\open\command` 手工指向一个存在的其他 exe，重启后确认未被覆盖；
- **破损自愈**：删掉 `URL Protocol` 标记后启动，确认标记被补回；
- **深链回调**：走完浏览器授权，确认软件被拉起并完成登录（日志中无 state mismatch）；
- **双实例路由**：开两个实例，各自登录，确认回调各回各家；
- **深链不可用时退回 HTTP**：把注册键删掉（且**跳过**启动时的补写，例如临时注释掉
  `ensure_registered()` 调用，或删键后立刻点登录），确认 `redirect_uri` 是
  `http://127.0.0.1:<port>/callback` 且登录照常完成；
- **前台激活**：确认浏览器授权完成后软件窗口到前台，而非在后台静默登录；
- **原实例已退出**：发起登录后关掉软件，确认浏览器授权时那个新进程正常启动（会多开一个
  窗口，需在新窗口重新登录）——这是接受的代价，不是 bug。

## 已知限制（本次不处理）

- **Win11 协议弹窗应用名显示为 `MoganSTEM.exe`**：Win11 从 exe 版本资源的
  `FileDescription` 取值，不再读注册表的 `ApplicationName`（安装器写入的
  `URL_APP_DISPLAY_NAME` 在 Win10 上生效）。而 `packages/windows/resource.rc.in`
  的 `FileDescription` 当前是 `"MoganSTEM.exe"`。本次不改该文件。
- **协议描述与 `ApplicationName` 用带空格的 `Liii STEM`**：与安装器
  （`tauri-installer` 的 `URL_SCHEME_DESCRIPTION` / `URL_APP_DISPLAY_NAME`）逐字一致。
  同一组键由安装器与运行时补写两方维护，值不同会让「谁最后写的」决定用户看到什么，
  故刻意不对运行时这边改用 `LiiiSTEM`。要统一得两个仓库一起改。
- **用户中途关掉软件后，那个 code 作废**：见「实例路由」一节。
- **`AllowSetForegroundWindow` 链路未经真机验证**：目前只有文档依据。
