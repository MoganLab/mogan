# [0532] OAuth 回调链路改造（四）：liiistem:// 自定义协议深链（Windows）

> **本任务分三轮。** 第一轮把回调通道整体切到 `liiistem://`（探测注册后深链优先），
> 提交于 `c163bb34e`；第二轮经浏览器实测推翻了该前提，深链**收窄为「纯唤起」**，
> 登录职能交回环回地址；第三轮把协议注册收归 mogan 独写（安装器侧删除该能力），
> 并加商业版门禁。下面 §1–§3、§6 各轮共用，§4 记录实测结论，§5 是第二轮的最终形态。

## 背景

承接 [0524]（redirect_uri 提取）、[0525]（端口系统动态分配）、[0526]（state 校验）、
[0529]（回调服务器按需监听与生命周期管理）。这四步都在完善**本地回环 HTTP** 回调通道，
而 [0524]/[0529] 的「后续」中记录了最终方向：把回调通道切换为 `liiistem://` 自定义协议，
由浏览器原生拉起软件。

切换到自定义协议的两个直接动机：

- **环回通道多实例场景脆弱**：虽然端口已改由系统分配（[0525]），但每次登录仍要占一个
  本地监听端口，且依赖杀软/代理不拦截回环请求；[0529] 为此加了 3 秒延迟关闭等容错。
- **协议通道是安装器既有能力**：tauri-installer 安装时已写入
  `HKCU\Software\Classes\liiistem`（见 [0524] 关联一节），浏览器授权后的 302 重定向
  本身即触发协议确认弹窗，官网前端无需提供任何额外按钮。

这两个动机在第一轮结束、第二轮开始后被部分推翻：环回通道的「脆弱」实测下来并不成立
（端口系统分配后多实例互不冲突，杀软拦截也没复现），而协议通道反而有**用户必须点一次
「始终允许」且该状态按 origin 记**的硬约束（见 §4）——它不适合承载每一次登录的回调。

## 现状（改造前的空白）

搜索确认，运行时侧与深链相关的能力**完全不存在**：

- 无 `QDesktopServices::setUrlHandler`、无 `QDesktopServices::registerUrlHandler`；
- 无 `QLocalServer` / `QLocalSocket`（项目也没有任何单实例机制，多开是常态）；
- 无注册表写入代码（`QSettings` 仅有一处未使用的 include）；
- `liiistem://` 只出现在 `QTMOAuth.cpp` 的注释里，标注为「后续」。

## 改动

本次只做 **Windows 单平台**。macOS（`CFBundleURLTypes` + `QFileOpenEvent`）与
Linux（`.desktop` 的 `x-scheme-handler`）留待后续。

### 1. 运行时写入协议注册（唯一写入方）

新增 `src/Plugins/Qt/oauth_deeplink_registry.cpp`，在 `research.cpp` 启动早期调用。

**这个键只有 mogan 写。** tauri-installer 侧原有的 `register_url_protocol` 已在本轮删除
（连同只被它使用的 `set_named_value`），单写入方，两个仓库不再各维护一套注册逻辑。
放在运行时而非安装时的理由：安装器只跑一次，

- 老 NSIS 用户（`packages/windows/research.nsis` 从不写这个键）升级到新版后，
  `HKCU\Software\Classes\liiistem` 永远是空的，深链直接失效；
- **Velopack 自动更新不会执行安装器**，静默更新用户永远不会再跑安装器。

判定表（「可用就不碰」，先来后到决定归属）：

| 当前状态 | 动作 |
|---|---|
| 键不存在 | 写 |
| 缺 `URL Protocol` 空值标记 | 写 |
| `shell\open\command` 取不出路径 / 指向的 exe 不存在 | 写 |
| 指向的 exe 存在（哪怕路径 ≠ 当前进程） | 不写，只记日志 |

**只有商业版执行**：`is_community_stem()` 为真时直接返回，不读也不写注册表。社区版
没有登录能力，深链对它毫无意义；更要紧的是它会**占住**这个键——本函数在注册可用时
一律不改写，社区版先跑一次，后装的商业版就拿不回来了。这里用运行时判定而非
`#ifndef IS_COMMUNITY`：对齐的语义是「有没有登录能力」，与
`StartupLoginDialog::shouldShow()` 同一个谓词，也不依赖本编译单元能否看到那个宏。

**值的落点必须对**：`shell\open\command` 与 `DefaultIcon` 要的是**子键的 (默认) 值**，
描述是 scheme 键的 (默认) 值，只有 `URL Protocol` 与 `ApplicationName` 是命名值。
`QSettings` 把键路径的**最后一段当值名**，直接写 `.../shell/open/command` 得到的是
`shell\open` 下名为 `command` 的值，Windows 找不到——浏览器既不弹窗也不报错，
只是静默无反应。末段补 `/Default` 时 Qt 会折叠成空值名（`qsettings_win.cpp` 中
`res == "Default" || res == "."` 即置空），正好落到子键的 (默认) 值上；
`kDefaultValueSuffix` 常量就是为此。

### 2. 深链接收与实例路由

新增 `src/Plugins/Qt/oauth_deeplink.hpp/.cpp`。

**URL 如何回到发起登录的那个实例**：唤醒 URL 形如
`liiistem://wake?instance=<instanceId>`，`instanceId` 是 `QTMOAuth` 构造时生成的
16 位随机串（早于 `login()`）：

```
新进程（浏览器拉起）
  ├─ 从 argv 认出 liiistem://
  ├─ 从 instance 参数切出 instanceId
  └─ QLocalSocket 连 "LiiiSTEM-URL-<instanceId>"
       ├─ 连上  → 写 URL → disconnect → 进程退出（全程无界面）
       └─ 连不上 → 原实例已退出，本进程照常启动，丢弃这个 URL
```

第一轮曾直接复用 `state`（其格式为 `<instanceId>.<一次性随机数>`）作为路由依据，
但唤醒与授权的生命周期不同：`state` 是一次性的、校验通过即清空，随机数部分对
「唤回前台」也没有意义。二者解耦后，`is_wake()` 只认 `instance` 一个参数。

每个实例在 `QTMOAuth` 构造后按自己的 `m_instanceId` 起一个 `QLocalServer`。多开时
socket 名天然不同，**不需要「主实例」概念，也不改变现有允许多开的策略**。

「连不上」时**不做接手**。曾设计过「新进程自己换 token，避免 code 白作废」，但这条路
结构上走不通：`m_state` 与 PKCE 的 `m_code_verifier` 都只在 `login()` 内生成，
新进程两者皆无——`handleCallback` 会因 `state` 为空直接拒掉，即便不拒，服务端也验不过
`code_verifier`。让用户在新窗口重新登录一次，比把 verifier 落盘去支持接手更简单也更安全。

### 3. Windows 会改写 URL（实测结论）

用临时 scheme + 原生 exe 实测 `%1` 的传递，发现 Windows 对 custom scheme URL
做了规范化：

```
送出:  LiiiSTEM://callback?code=ABC-123&state=inst42.nonceXYZ
收到:  liiistem://callback/?code=ABC-123&state=inst42.nonceXYZ
       ↑ scheme+host 转小写        ↑ query 前多一个 /
```

因此实现中：

- scheme 判定大小写不敏感（`QUrl::scheme()` 本身也会返回小写）；
- 不依赖 `path()` 判断意图，只取 `QUrlQuery` 的 `instance`，忽略 host 与 path。

同一轮实测还确认了两点：

- `shell\open\command` 中 `%1` **必须带引号**（安装器现有写法正确）。实测带引号时
  完整送达 `"liiistem://callback/?code=ABC-123&state=..."`；URL 里的 `&` 不会截断参数，
  因为这条路径不经过 `cmd.exe`，无 shell 元字符解释。
- `URL Protocol` 空值标记是**硬性必要**。漏写时 `ShellExecuteW` 直接返回
  `31 (SE_ERR_NOASSOC)`，应用根本不启动；补上后才返回 `42` 并成功拉起。

### 4. 实测：浏览器侧的自定义协议策略

第一轮的方案默认「授权成功后 302 到 `liiistem://callback` 就能把 code 交回软件」。
用临时 scheme（`liiistemprobe`）+ 探针页面在 Edge 上实测，得到三条决定性结论。

**结论一：页面能否唤起协议，取决于「(来源 origin, scheme) 是否已被用户永久允许」。**

| 该 origin 的允许状态 | 无手势的 JS 跳转 | 用户手势（点击） |
|---|---|---|
| 未允许过 | 弹确认框，需点「打开」 | 弹确认框，需点「打开」 |
| 已点过「始终允许」 | **静默拉起** | 静默拉起 |

允许状态存在 profile 的 `Preferences` 里，键为
`protocol_handler.allowed_origin_protocol_pairs`，**按「发起页面 origin（含端口）+ scheme」
作 key**，且跨浏览器重启保留（实测：优雅退出后重启 Edge，无手势跳转仍静默拉起）。

注意**手势不是门槛**——未允许时首次点击同样要过确认框，允许之后无手势也能拉起。
（曾误判为「无手势跳转被静默丢弃」：全新 profile 下确实毫无反应，实为那个窗口当时
未获焦点，确认框没被截到；换到前台窗口复现，确认框照常出现。）

**结论二：环回回调页拿不到这份允许状态。**

回调页的 origin 是 `http://127.0.0.1:<系统分配端口>`（[0525]）。端口每次登录都不同，
origin 每次都全新，`allowed_origin_protocol_pairs` 里永远没有对应条目——**从回调页发
深链，每次登录都会弹确认框**（还可能是用户刚把视线移开的时候）。成长激励页则是官网的
固定 origin，用户点一次「始终允许」之后永远静默。这正是「由成长激励页发唤醒」的理由。

**结论三：服务端 302 到自定义协议与页面内跳转同规则。** 实测 `/redir` 返回
`302 Location: liiistemprobe://callback?code=REDIR-CODE&state=...`，URL 完整送达进程
（`&` 未被截断，走的是 `ShellExecute` 而非 `cmd.exe`），未获允许时同样先弹确认框。

### 5. QTMOAuth 接入（第二轮定稿）

深链的职责收窄为**纯唤起**：授权码由环回回调收下，深链只把软件窗口提到前台。这样
既不需要服务端白名单放行 `liiistem://callback`，也不用把 `state` 的 CSRF 语义与
「唤回前台」的实例路由语义混在一起。

- `redirect_uri` 恢复恒定取环回地址：`login()` 中 `m_redirectUri= m_reply->callback ()`，
  授权请求与令牌交换两处仍逐字节一致（RFC 6749 §4.1.3）。`kRedirectUri`、
  `redirect_uri()`、`m_deepLinkChosen` 一并删除。
- `handleDeepLink()` 只做两件事：`is_wake()` 判定通过后 `bring_to_front()`。不再构造
  `QVariantMap` 调 `handleCallback`，也不做 state 校验。
- `state` 回到**单纯的一次性随机数**：第一轮把实例标识夹在 `state` 里
  （`<instanceId>.<随机数>`，[0526] 引入）是为了让回调 URL 自带路由信息，如今路由
  改由 `instance` 参数承担，这段前缀已无人读取，留着只会让两套语义继续纠缠。
- `refreshCallbackHtml()` 在跳往成长激励页的 URL 上追加 `instance=<本实例标识>`。
  growth-url 自带 query（`?from=oauth&version=v<xmacs-version>`），故用 `&` 追加；
  `m_instanceId` 只含字母数字，无需转义。
- 官网成长激励页读到该参数后跳 `liiistem://wake?instance=<值>`。**只传实例标识、
  不传完整 URL**：成长页是公开页面，若允许调用方塞一个完整 URL 进去再 `location.href`
  就等于开了一个开放重定向。

第一轮的设计（深链优先、`deep_link_usable()` 探测、`deep_link_usable()` 失败时退回
HTTP）随之全部移除；`ensure_registered()` 与实例路由、前台激活链路保持原样。

**关于「注册指向别的副本」**：第一轮靠 `deep_link_usable()` 比对注册表里的 exe 与
本进程来规避「老版本收到深链只开个空窗口」。收窄为纯唤醒后这个风险不存在了——最坏
情况是别的副本被提到前台，不影响登录。`ensure_registered()` 依旧遵循「指向的 exe 仍
存在就不碰」，不做抢占。

### 6. 前台激活

新进程是浏览器拉起的，有权抢前台，但它只是转发器、几毫秒后即退出。老实例收到 URL 时
前台焦点仍在浏览器上，而 Windows 默认拒绝对非前台进程的 `SetForegroundWindow`，
结果是浏览器亮着、软件在后台静默登录完成。交接分两半，都在 `oauth_deeplink.cpp`：

1. 转发进程在连接成功后调 `AllowSetForegroundWindow(ASFW_ANY)` 让出前台权；
2. 目标实例在 `handleDeepLink()` 里调 `bring_to_front()`：优先挑 `QMainWindow`
   类型的可见顶层窗口（顶层里还混着搜索栏与各种 popup），最小化时先 `showNormal()`，
   再 `activateWindow()`。

使用 `ASFW_ANY` 而非反查 pid（`GetNamedPipeClientProcessId`）换取实现简单，
代价是那几毫秒内任何进程都能抢前台。如需收紧，后续改为按 pid 精确授权。

`AllowSetForegroundWindow` 有前置条件、可能失败。失败不致命（登录照常完成，只是
窗口不弹出来），故只记一条 `debug_boot` 日志而不中断流程——真机上若发现窗口没动静，
日志里能看到是不是卡在这一步。

### 7. 单元测试

新增 `tests/Plugins/Qt/oauth_deeplink_test.cpp`，覆盖纯解析逻辑（xmake 自动发现）：
正常唤醒 URL、Windows 规范化后的 `scheme://host/?...` 形态、scheme 大小写、参数顺序、
`instance` 缺失或为空、非 liiistem scheme；`find_url` 跳过 `argv[0]`。

注册表写入与实例转发要碰真实系统状态（HKCU、本地 socket），不进单元测试，靠下面的
手工验证。

## 验证

- **老用户态**：删除 `HKCU\Software\Classes\liiistem` 后启动，确认键被按当前 exe 路径补上；
- **仅商业版**：用社区版构建重复上一条，确认键仍为空；再手工写入一个正确的键，
  用社区版启动，确认它没被改写；
- **不抢占**：把键的 `shell\open\command` 手工指向一个存在的其他 exe，重启后确认未被覆盖；
- **破损自愈**：删掉 `URL Protocol` 标记后启动，确认标记被补回；
- **登录仍走环回**：抓授权请求，确认 `redirect_uri` 是 `http://127.0.0.1:<port>/callback`
  且令牌交换用的是同一个值；
- **成长页带参数**：检查回调页跳转目标，确认 growth-url 上多了 `&instance=<16 位串>`；
- **前台激活**：走完浏览器授权，确认软件窗口到前台，而非在后台静默完成；
- **双实例路由**：开两个实例，各自登录，确认各回各家（另一个实例的窗口不动）；
- **协议未注册时的降级**：删掉 `HKCU\Software\Classes\liiistem` 且**跳过**启动时的写入
  （例如临时注释掉 `ensure_registered()` 调用），确认登录照常完成，只是窗口不会被提起
  ——这正是「深链只是增强」的含义；
- **原实例已退出**：发起登录后关掉软件，确认浏览器授权时那个新进程正常启动（会多开一个
  窗口，需在新窗口重新登录）——这是接受的代价，不是 bug。

### 待官网侧配合

**成长激励页需按 `instance` 参数跳 `liiistem://wake?instance=<值>`**，这是本方案在
浏览器侧的唯一外部依赖。页面不认识该参数时行为不变（登录照常完成，只是窗口不被提起），
因此可以与本版解耦发布。

## 已知限制（本次不处理）

- **Win11 协议弹窗应用名显示为 `MoganSTEM.exe`**：Win11 从 exe 版本资源的
  `FileDescription` 取值，不再读注册表的 `ApplicationName`（该值只在 Win10 上生效）。
  而 `packages/windows/resource.rc.in` 的 `FileDescription` 当前是 `"MoganSTEM.exe"`。
  本次不改该文件。
- **协议描述与 `ApplicationName` 用带空格的 `Liii STEM`**：这两个值对外可见
  （资源管理器里、浏览器确认框上），沿用安装器此前的文案，免得存量用户看到的名称
  突然变样。安装器那边的常量（`URL_SCHEME_DESCRIPTION` / `URL_APP_DISPLAY_NAME`）已随
  `register_url_protocol` 一并删除，现在只有运行时这一处，改文案只需动这里。
- **用户中途关掉软件后，那个 code 作废**：见「实例路由」一节。
- **`AllowSetForegroundWindow` 链路未经真机验证**：目前只有文档依据。
- **唤醒依赖官网成长页改版**：页面不发跳转就没有置前效果。见「待官网侧配合」。
- **回环通道短期内不退役**：它现在是唯一收码通道，不像第一轮那样指望着被替换。

4. 若要彻底去掉回环通道，还需先解决「回调页 origin 每次登录都变、拿不到用户的
   「始终允许」状态」这一约束——否则只能退回到「由官网固定 origin 的中间页收码」，
   而那要求服务端白名单放行该页面的 redirect_uri，属于另一次改动。
